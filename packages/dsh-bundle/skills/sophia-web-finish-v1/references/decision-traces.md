# Decision traces

Read only to observe how a brief becomes an implementation. These are anonymized, abstracted examples of judgement order, evidence types and correction; they are not CSS, palettes, sizes, layouts or templates. If an artifact's surface converges on an example, routing failed. [D0.1]

## Editorial content: multiple kinds of evidence supporting an argument [D2.1–D2.6]

**Brief reading.** The artifact must let the reader form an understanding through narrative, people or place material, data and method notes. The main task is reading in the author's order, comparing evidence and forming a view, not operating a content system. The natural form is continuous editorial reading; length, evidence types and reading context decide scrolling.

**Rejected defaults.** Paper colour, oversized serif titles, hairlines and numbering taken as automatically "editorial"; app navigation, control panels or metric cards instead of chapter structure; abstract imagery filling a content gap.

**Benchmark mechanisms.** From mature editorial publications: chapter semantics first, a grid that holds heterogeneous content, type divided by information role. From rigorous documentary and research deliverables: which evidence responsibility images, quotations, data and captions each carry. Never copy column names, proprietary type, brand symbols, cover compositions or specific colour answers.

**Decisions.** The first visual is one clear argument plus the most explanatory evidence, without generic app navigation. Continuous reading, unfolding evidence and short pauses make the rhythm; proportions and interleaving derive from content. Colour derives from subject, medium and information roles, never a habitual "premium" colour.

**Render finding and fix.** Finding: too many elements compete in the opening, with no stable first point of attention. Root cause: every piece of background was judged essential to feature at the start. Fix: keep only the core argument, the key evidence and necessary attribution; move method, dates and details back to their most relevant reading place. Recheck: thumbnail centre of gravity, normal measure, caption ownership, evidence order, and reading continuity at the narrow width.

**Transferable conclusion.** An editorial artifact's quality comes from content order, evidence roles and reading rhythm. "Like some magazine" is not a direction.

## Data story: comparing groups and change over time [D3.1–D3.6]

**Brief reading.** The reader compares speed, scale, difference and distance from target across groups or periods; the task is seeing the pattern and understanding the evidence, not managing the business objects behind the data.

**Rejected defaults.** A fixed number of metric cards plus a set of common charts assembled into a business dashboard; topic colours and symbolic icons instead of a data argument; units, sources, key values and uncertainty hidden in hover text.

**Benchmark mechanisms.** From mature public data products: complete statistical context, encodings matched to the task, sources and units, and an equivalent table. From rigorous data stories: one figure advances one main point; annotation and text build the reading order together.

**Decisions.** First write an argument the data could refute, then choose the form. The object carrying the main comparison is the first visual; secondary evidence follows the argument, not equal containers. Tables, labels and summaries come from the same source. Colour encodes category, order, threshold or deviation, never decoration.

**Render finding and fix.** Finding: the comparison is prominent but its statistical context is squeezed into low-contrast small text, so the reader cannot verify it. Root cause: units, sources and key values misjudged as secondary metadata. Fix: units in the title or header, key values labelled directly, the source in a stable visible place, repeated legends and decorative metrics deleted. Recheck: extreme values, the densest labels, the narrow width and keyboard reading of the table.

**Transferable conclusion.** A data artifact's beauty is first a clear comparison, an honest scale and precise annotation. A library's default theme and a dashboard skin cannot replace judgement.

## Cross-example rules [D5.1]

1. Choose the domain by the main task, never by HTML, framework or file type.
2. Benchmarks give mechanism and quality, never a copyable skin.
3. Mature means carry general capability; task-specific expression carries subject and content.
4. Images, graphics and interaction enter only when they carry information or operation.
5. The first vertical slice verifies the direction, so a wrong direction is not expanded into a complete artifact.
6. Render review names the visible symptom first, then traces content, composition, material or technique.
7. "Less" is not the goal; "everything has a job" is. Dense and rich can be refined too.
