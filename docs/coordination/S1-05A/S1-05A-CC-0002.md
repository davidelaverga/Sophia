## What to resolve (read only)

1. **Where the candidate's long-running processes would run.** The pack assumes one private execution VM. Report which of these exists today, and its identity:
   - a Render background worker;
   - a VM;
   - nothing yet.

   The processes are `apps/worker` (runtime dispatch and guest removal), `apps/media-bridge` (LiveKit RTC ↔ Gemini Live) and `scripts/runtime-host.mjs` (the pinned dsh runtime).
2. **Settings presence (`set`/`unset`/`blank`, never values), per service.** Names are as in `.env.example` at the candidate:
   - **API:** `SOPHIA_MEDIA_BRIDGE_TOKEN_SHA256`, and `LIVEKIT_URL`/`LIVEKIT_API_KEY`/`LIVEKIT_API_SECRET`.
   - **Worker:** `SOPHIA_WORKER_DATABASE_URL`, and the same three `LIVEKIT_*`.
   - **Bridge:** `SOPHIA_SERVICE_URL`, `SOPHIA_MEDIA_BRIDGE_TOKEN`, `GEMINI_API_KEY`, `SOPHIA_LIVE_MODEL`.
   - **Execution host:** `SOPHIA_SERVICE_URL`, `SOPHIA_RUNTIME_TOKEN`, `OPENAI_API_KEY`.

   As the issue body notes, `GOOGLE_API_KEY` on the API is not read by any candidate code; the bridge reads `GEMINI_API_KEY`.
3. **Database roles (booleans).** Does a login granted `sophia_worker` exist, and is it distinct, non-owner and non-BYPASSRLS?
4. **LiveKit traces.** In what form can the operator read them (dashboard sessions or an export)? What identifies a session (room sid `RM_…`)? What is the retention window? Status only.
5. **One diagnostic run.** First review [`apps/api/scripts/diagnose.ts` at this commit](https://github.com/davidelaverga/Sophia/blob/2f76776df2864dea9a3dfccb6d851cc0359b1ebd/apps/api/scripts/diagnose.ts). It opens one `BEGIN READ ONLY` transaction and ends it with `ROLLBACK`, and it only lists LiveKit rooms and participants. Then, from a checkout of that commit, with `pnpm install --frozen-lockfile` and Node 24.21.0:
   ```
   SOPHIA_DIAGNOSE_DATABASE_URL=<migration-owner URL, verify-full> LIVEKIT_URL=… LIVEKIT_API_KEY=… LIVEKIT_API_SECRET=… \
     node apps/api/scripts/diagnose.ts --limit 20
   ```
   Its JSON is sanitized by design: 8-character ids, no tokens, names, emails or text. Check it before posting. Tables from 0012–0014 will show `does not exist` on a database without those migrations; that is expected, and useful.

## Standing evidence contract for later production debugging

Reply per incident with a UTC time window, then:
- **Deployments:** every service's deploy id and source commit.
- **The diagnostic:** its output, scoped with `--project <uuid>` if there is one.
- **Bridge log lines in the window.** These are JSON, filterable by `exchangeId`, and carry no content. Events: `session.start`, `room.joined`, `provider.ready`, `assignment.changed`, `tool.answered` and `tool.dropped`, `provider.recover`, `session.unavailable`, `session.lost`, `room.connection`, `presence.report_failed`, `quiesce.ack_failed`, `holder.event_failed`, `audio.*`.
- **API lines with status ≥ 400** on `/v1/media/*`, `/v1/runtime/*` and `/api/v1/{rooms,exchanges,lobby}/*`. Include method, path without query, status, `reqId` and error `code`.
- **Worker `[sophia-worker]` lines.**
- **The LiveKit trace for the room sid:**
  - joins and leaves, with identity class only: `sophia`, member-8, or guest-8;
  - track publish, subscribe and unsubscribe for `sophia` and the floor holder;
  - `sophia.*` attribute changes;
  - disconnect reasons and connection quality.
- **Browser:** the text of Sophia's line, which Sophia dock buttons were shown, and console errors.

Never include audio or video, transcripts, tokens, signed links, names or emails, full UUIDs, or raw database rows.
