## P2 — recheck membership after the project lock in conversation_locked

Location: `db/migrations/0048_project_conversations.sql`, `conversation_locked` and its use by `withdraw_conversation_message`. The helper tests `is_member` before waiting for the project's row, and does not test membership again after acquiring it. Withdrawal's own-author branch then permits removal without another membership check. `conversation_writer` protects start/send; it does not run for withdrawal, correctly allowing a current viewer to withdraw their own message.

**Expected:** an author may withdraw while still a project member, including a viewer. A caller revoked while waiting cannot commit a withdrawal or replay through the SQL writer.

**Observed independently, real PostgreSQL17.6, non-owner API login:** the caller was revoked before its blocked writer acquired the project lock; `withdraw_conversation_message` returned success and committed `body=NULL`. The independent assertion failed with `{accepted:true,body:null}` instead of `{accepted:false,body:'Synthetic body to preserve'}`. This is a SQL boundary finding; it is not yet a demonstrated HTTP exploit. The route reads back under RLS in the same transaction, which may refuse and roll back. That separate crossing is being checked.
