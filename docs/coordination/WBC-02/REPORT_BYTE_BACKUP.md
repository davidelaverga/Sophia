# Report object backup on the existing API service

Source preparation for Davide's 12 October 2026 direction: reuse Supabase and the renderer, add private Paperclip and a paid API, retain daily backups, defer new voice qualification, and keep the cumulative $25 / 10-image test ceiling. Nothing in this document activates a resource, creates access or authorizes a production deployment.

## The gap and the selected mechanism

Supabase's daily database backups contain object metadata, not the report bytes in Storage. The existing `sophia-next` project already has daily **PHYSICAL** backups; Codex observed snapshots dated 5–12 October, including 12 October 11:14:35 UTC. Those are project/cluster recovery, not a qualified Paperclip-only restore.

The API can keep an immutable, flushed copy of each object on its own small persistent disk **before** uploading the same bytes to Storage. Render automatically snapshots persistent disks every 24 hours and retains snapshots for at least seven days. This uses the existing API service; no backup scheduler, new worker, broader storage credential or database credential on Paperclip is introduced.

Proposed final-batch resource: one 1 GiB disk on `srv-daqrn08473hc73flhi8g`, mounted at `/var/data/report-byte-backup`. Indicative marginal disk cost $0.25/month, to be checked on the final account form. The proposed paid API is the account's $7/month 0.5 CPU / 512 MB plan. Adding a disk prevents overlapping instances and zero-downtime deployment; the release batch must account for that brief API restart.

## Configuration and states

`SOPHIA_STORAGE_BACKUP_ROOT=/var/data/report-byte-backup` enables copying; absent disables disk copies; configured S3 writes still receive bounded cancellation/deadlines and retained-write admission. The five existing `SOPHIA_STORAGE_*` S3 settings remain all-or-none. Setting only a backup root is refused.

- Startup requires an existing canonical absolute root that is a dedicated, non-volatile mount in Linux's actual mount table. An absent disk is not created as an ephemeral fallback. The provider disk ID, mount and persistence across recreation must still be verified on Render before admission.
- The API creates/checks its own `objects/` and project subdirectories at mode 0700, owned by its effective user. It refuses symlinks and directories readable by other users.
- Only canonical lower-case `<project UUID>/<source UUID>` keys and objects up to 32 MiB are accepted. Copies live at `objects/<project UUID>/<source UUID>`, with the **exact original bytes** and mode 0600. MIME and authoritative SHA-256 stay in the database records; backups do not create a second content catalogue.
- The existing database write-once claim still commits before this store is invoked. A private temporary file is opened exclusively, written and fsynced. A hard link commits its immutable final name without replacing an existing file. Parent directory entries are flushed too. Only then may the remote PUT begin.
- A capture route derives its source UUID from the server-validated project, job, lease and capture name with a fixed, domain-separated SHA-256 encoding. The SQL slot still authorizes the real capability/lease; its unused random UUID is discarded. During that lease, the first name claims its one key, and any replay (including different bytes, concurrent requests, a recreated API or an uncertain first write) is refused with409 **before** another backup/remote PUT. This is write-once refusal, not an idempotent200 or automatic recovery of an uncertain object. A renewed valid lease gets a fresh key:0045 removes the lost lease's output associations and0039 records the new run's captures. Every new lease's actual copy remains charged. The database job state limits ordinary automatic claims to three, but human Hold/Resume can admit more generations; there is no universal three-copy lifetime promise. Distinct names still consume their ordinary budgets.
- Before creating a project directory or temporary copy, the API reserves its payload bytes and one object in a durable private SQLite journal on that same disk. Fixed pilot ceilings are 768 MiB / 4,096 objects overall, 256 MiB / 1,024 objects per project and 96 MiB / 144 objects per renderer job. Both PDF and PNG routes supply the job UUID only after validating the capability and lease; all byte-store wrappers forward it. Ordinary uploads still charge the global and project ceilings. A repeated capture name gets a fresh key only under a renewed validated lease; every such generation remains within its stable job's cumulative allowance. Same-lease replay is refused before a new durable claim, backup reservation or PUT. Capture retry SQL and its new-lease association reset remain unchanged.
- Admission is an atomic SQLite transaction across processes and restarts, with `synchronous=FULL`, a rollback journal, a 4 KiB page size and at most 2,048 pages (8 MiB database plus bounded rollback-journal space). The journal and its directory are private (0600 / 0700). Duplicate keys are refused with 409; exhausted capacity, contention, corrupt/missing journals, partial initialization and unavailable space are refused with 503, before copying or remote I/O. An existing object directory is never adopted into a new empty journal. Failed and uncertain writes retain their reservations permanently; ordinary retries, API recreation and database rollback never reset them. Refused requests add no rows.
- The transaction also requires at least 128 MiB free **after subtracting the new write and every prior reservation from currently available space**. This deliberately double-counts completed copies to cover concurrent copies conservatively; admission can stop before the nominal byte ceilings. There is no automatic capacity increase or reclamation. A bounded worker performs synchronous SQLite/filesystem admission away from the API event loop, receives no report bytes or credentials, and has a five-second deadline. At most two quota workers are admitted in one process, with no waiting queue; timed-out workers retain their slots until actual exit. A valid success message permits copying only after clean worker exit. A late commit remains charged and never starts a copy. Payload/count ceilings separately bound concurrent copy growth; worker slots do not limit the number of copies already admitted.
- A failed, full, unavailable or slow backup refuses the upload. Copying has a ten-second application deadline. An operation that completes late can leave a private orphan, but cannot continue to a remote upload. The database claim is never released or reset by this code.
- If the remote PUT fails after copying, keep the copy and the uncertain claim. There is no automatic replay, refund, import or publication. A later retry still meets the ordinary database claim guard.
- Reads and signed URLs still use the existing authenticated Storage path. There is no backup reader route, local fallback or public backup URL.

## Retention and recovery

Live copies have the same retention obligation as the primary immutable report objects. They are not automatically erased by a database rollback or by a source's loss of read eligibility. Snapshot copies remain under Render's provider retention policy, **at least** seven days; this is not a promise of physical erasure within exactly seven days. Governed physical deletion must include both locations when it is performed. This source change performs no deletion.

Before deployment, retain the existing source/data census and a compatible PostgreSQL 17 logical export for the approved operation. Paperclip's persistent home separately uses its own Render disk's daily snapshots; its database stays in Supabase. Do not enable the unqualified JavaScript backup fallback in the upstream Paperclip pin.

Recovery is operator-controlled: close affected admission and settle/fence writers, choose compatible database and disk recovery points, match each copied object's canonical identity and SHA-256 to the restored ledger, then restore only missing approved bytes. Preserve the quota journal with the copies, including charges without a surviving copy; never delete, recreate or reset it to reopen admission. A copy is not evidence that its source was published or remains eligible. Never overwrite a surviving object with different bytes or silently recreate a missing governed record. Reconcile Paperclip issue bindings with Sophia's ledger before reopening coordination.

Daily snapshots across providers are not atomic. A paired restore may require an older common recovery point; a strict whole-system 24-hour RPO is not proven by the cadence alone. Missing or inconsistent evidence stays unavailable. A project-wide database restore or a destructive disk restore requires its own actual recovery authority; ordinary rollback does not invoke either.

The 1 GiB size is a bounded pilot choice. Check free space and byte growth on the actual disk; a full disk stops new object writes. No automatic resizing, deletion or resource upgrade is permitted. Snapshot encryption at rest is provided by Render, not an application encryption key introduced by this patch.

## Qualification and rollout

Unit tests use real temporary filesystem I/O and a **labelled mount-table fixture**. They exercise copy ordering, first-writer behavior, permissions, traversal/symlink refusal, immutable inputs, byte/count ceilings, independent-process races and restart persistence, retained charges after failures, journal refusal and bounded worker deadlines. Real HTTP/PostgreSQL tests verify stable job identity through both PNG and PDF uploads. These checks do not prove a mounted Render volume, a Supabase upload or provider snapshot recovery.

Before a production grant: bind the final source and deployment IDs; attach the actual API disk; prove the mount, free capacity, private journal/directories and worker/SQLite behavior; upload one labelled synthetic object through the deployed API; compare its database SHA, Storage bytes, disk copy and durable reservation; recreate the API on the same disk and compare again; verify the daily snapshot is available when one is due. Keep new admission closed on any failure.

The final batch separately retains Supabase's daily backups, the Paperclip home disk and the cross-system recovery procedure. New voice qualification remains off, with PR #190's two billing findings open. This change touches no migration, runtime bundle, native role, prompt, contract or Studio path.

## Upload memory and deadline admission (PR #270 automatic review follow-up)

Each upload starts one absolute ten-second request deadline before authorization; authorization and body receipt share that original budget. The timer closes a stalled request even if its database operation is still pending, and late success cannot admit or parse it. A separate process-wide gate permits at most16 original authorization operations across API app factories, acquired before invocation and retained until actual settlement, including after timeout/disconnect; overflow never invokes another database operation. This is not database cancellation or per-project fairness. Authorization failures, body-admission refusal and pre-handler exits clear the timer only if the raw body is complete or the socket closed; otherwise its original deadline survives the prompt refusal response until body completion/close. This includes early parser errors after byte admission. A raw close also settles the public authorization wait, while the original database-operation permit remains held until actual settlement. An admitted body retains its timer until parsing completes. Before reserving body capacity, each upload calls the existing database output/capture slot operation to validate the active runner capability and owned running lease, with explicit pre-schema job/lease/name checks. This preflight updates runner seen_at and briefly locks the job; it creates no source/write claim and does not extend the lease or add a new lease-expiry rule. The generated unused UUID is discarded. The handler repeats ordinary slot validation after parsing so capability/lease changes still refuse storage. A request disconnected during authorization is refused before admission, preventing a missed-close permit leak. Global bearer-shape validation alone is not this authentication. Each API process admits at most four renderer PNG/PDF requests and 64 MiB of their route maxima before buffering bodies (32 MiB per PDF, 8 MiB per PNG), irrespective of Content-Length. A ten-second body-read wall/monotonic deadline destroys an unfinished request; completed handlers release and clear their request bodies, while client disconnects during handling do not release early. Separate process-wide write admission allows at most two writes and 32 MiB of retained payloads, with no waiting queue. With backup enabled these are snapshots admitted before allocation; with backup disabled they are the original payloads, with no snapshot or disk copy. Both states create the same bounded cancellation/deadline control and share admission until actual S3 settlement. This conservative write limit admits one maximum32MiB PDF at a time even though raw-body admission can parse two. Permits survive public ten-second whole-write timeouts until the underlying disk, if enabled, and remote operation truly settle; late disk completion cannot begin a remote upload. The entire wrapper preserves earlier incoming cancellation/deadlines, including expiry during snapshot allocation without leaking admission. The S3 adapter receives cancellation and a monotonic deadline, checks both before signing and again immediately before HEAD/PUT, and never starts a late PUT after a delayed HEAD. An already accepted PUT can remain uncertain; its claim, charge and memory admission are retained until real settlement. Remote errors are sanitized, with existing-object conflicts still409. At most two quota workers, including timed-out workers awaiting exit, remain admitted.

These are bounds on upload bodies/snapshots and quota-worker count, not proof of total API RSS or all buffered reads. Fastify can temporarily retain both chunks and their concatenated body; renderer GET file, normal JSON requests, database/runtime baseline and allocator overhead remain outside these counters. Production qualification must verify the 512 MiB API under the pilot workload, and stop admission on OOM or uncertainty. No count or byte gate is per-project fairness, a queue, cancellation guarantee, or refund.
