## 1. WBC-02-CX-0013: every status write is settled, whatever its call did

The finding is right. At `414924f` the plugin settled only after an effect returned. An original Hold that wrote `blocked` after a later Stop and then failed skipped settlement. Its retry answered `already` from the row its resend had applied. The issue stayed `blocked`. The pin makes that ordering real: `issues.update` commits, then the activity log is written, and only then does the host answer (`plugin-host-services.ts` 1965–1988).

`packages/paperclip-plugin/src/coordination.ts`, with a new namespace table `effects` (`migrations/001_sophia_coordination.sql`):

- **Every status write is recorded before it is asked** (`writeStatus`). It ends when the host answers, with the issue or with an error: the pin answers a worker call only once its handler has finished (`plugin-worker-manager.ts` 2697–2740), so whatever the call wrote is in place by then. A call the host never answered is different: the worker's own 30 s timeout, `JsonRpcCallError` -32003 (`worker-rpc-host.ts` 208, 383–415), which `bind.ts` maps to `UnansweredHostCall`. Such a call may still land, so it stays open, as does a write whose worker died. Either counts as ended only once stale (120 s, four times that timeout).
- **Every control effect ends with a settlement, whether it returned or failed** (`applyControl`, in `finally`; `settleAfter`). The settlement runs under this delivery's lease while it still holds it, otherwise under the lease taken again. It reads the issue after the writes ended. If the issue shows a status that an open write may have made, but not the status of the latest control Sophia sent, that status is written again. That write is itself recorded and settled in the next round. The writes that ended before the read are then settled.
- **No delivery is answered done while a write of its commission could still change the issue.** Neither `applied` nor `already` is sent until then; the answer is 503 `effect_unsettled`, which the worker records as unknown and asks again (backoff up to 5 min, no give-up). A resend answered from its record settles open writes first (`confirmSettled`). That covers the already-applied retry of your sequence. The control's row is still marked `applied` once its own write returned, which is what the superseded check reads. Only the answer to Sophia waits.
- **A settlement that cannot take the lease, or whose own calls fail:** the writes stay open, nothing is answered done, and the holder of the lease settles before it answers. The plugin's new scheduled job settles every open write every minute, without waiting for Sophia's next delivery: `settle-status-writes`, `* * * * *`, capability `jobs.schedule`, registered in `setup`.
- **A call or a settlement that outlives its lease:** the lease is now 60 s, twice the worker's host-call timeout, and is renewed before each write. A write is therefore begun only by the delivery that holds the lease. A delivery whose lease ran out before it wrote writes nothing and is answered 503 `control_in_progress`. A settlement's own write is recorded and settled like any other.
- **The host's own states and Sophia's fences:** only a status that an open write may have made is ever overwritten, and only with the status of the latest control Sophia signed. Rows exist only after the envelope is verified. A status like `in_progress` after a Resume is left alone. Wakeups are not settled: a wakeup asked late can queue a run, which Sophia's permit denies, ending it as a completed run (`sophia_permit_denied`).

Your sequence at this head (`coordination.db.test.ts`, the synthetic host with an update held in flight and then failing after its write):

| Step | `414924f` | Now |
|---|---|---|
| Original Hold held in its update; lease expired; its resend | `applied` | `applied` (the write in flight can only set what the Hold wants) |
| Stop | `applied`, issue `cancelled` | 503 `effect_unsettled`, issue `cancelled`, row `applied` |
| The original writes `blocked`, then the host answers an error | issue stays `blocked` | settled to `cancelled` before its error is answered |
| Stop and Hold resent | `already`, issue `blocked` | `already`, status `cancelled`; no open write; lease released |

One behaviour changes for the worker: a Stop sent while an earlier Hold's write is still in flight is answered 503 until that write ends. The CX-0008 test now asserts that.

New tests:

- a settlement that itself fails: nothing is confirmed, and the settle job settles it;
- a write the host never answered that lands late: undone at once, but the Stop is confirmed only once that write is stale;

### 2.2 Runtime: the old unit's six live bindings are drained, never forced final

How bindings are served, from the code:

- A binding belongs to its runtime unit (`execution_bindings.runtime_unit_id`).
- A runtime serves only its own unit's bindings (`0012` line 590: `runtime_unit_id=rt.runtime_unit_id`).
- A continuation stays on the binding's unit (`0028`, `0033`: `b.runtime_unit_id`; `0037`, `0042`: `runtime_unit_id=b.runtime_unit_id`).
- New work picks any active runtime instance that declares the role and route, available first, then most recently seen (`sophia.work_runtime`, research admission). Two units may be active side by side (`one_active_runtime` is per resource and unit).

Replacing `sophia-next-runtime`'s unit would therefore strand the six `running` bindings on `sophia-runtime-m03-dev`: they could neither continue nor settle. They must not be marked `settled` or `lost` to satisfy the cutover. The architecture says the same: keep the previous unit available to drain existing work (`docs/pack/architecture/02_DSH_BOOTSTRAP.md`).

**Per-binding qualification (Codex, read-only).** For each binding of the old unit in `created`, `launching`, `running`, `idle` or `stopping`, read:

- its attempt and job (kind and state);
- its goal (state and authority epoch);
- its outstanding runtime commands and outbox rows, with their receipt stages and any `outcome_unknown`;
- the binding's last change and its runtime instance's `seen_at`.

Classify each one:

- **live:** it is progressing and ends on its own;
- **settling:** its goal is held, stopped or finished, and it settles through its own path while its unit runs;
- **no progress:** it goes to Davide, who decides through that work's own controls (its owner's Stop) or leaves it as is. A release never changes its state.

**D6 (Davide): how the combined unit goes live.**

- **A. Drain in place (no new infrastructure).**
  1. Release the database, API, worker and Studio at the batch commit, and keep `sophia-next-runtime` on `sophia-runtime-m03-dev`, built from its own commit.
  2. Once the old unit has no binding left outside `settled` or `lost`, reached by each binding's own path, cut the runtime over to the combined unit.
  3. Until then, a review or a design answers `runtime_unavailable`, because no active runtime declares those roles, and research continues on m03.

  Qualification before the API moves: the m03 runtime host, at its commit, against the batch API and database on a disposable copy. It must run a research task's turn, Hold, Resume, Stop and settlement. This is the continuation qualification.
- **B. Side by side.**
  1. Add a second runtime host for the combined unit beside the m03 one: a new Render worker with its own disk, registered with `scripts/register-runtime.ts` under its own capability.
  2. New work goes to an active runtime that declares its role and route. Research may still land on either host, which can lengthen the drain. Every existing binding stays with its own unit.
  3. Stop the m03 host only once its unit has no non-final binding.

  This is new infrastructure, so it needs Codex's cost quote and Davide's hosting decision, as D4 does.

Whether the combined unit could resume an episode copied from m03 has its own on-request check: SMC-M02's `tests/integration/log-compat.test.mjs` (M02-T12/T13). It exports a held episode on one unit and imports it into a fresh home of the other. It is the evidence for any continuation across units. It moves no live binding, though, and no database operation rebinds one to another unit, so it does not replace the drain.
