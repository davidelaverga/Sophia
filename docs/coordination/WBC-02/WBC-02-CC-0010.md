### 2.1 The Paperclip image, delivered by digest

Render cannot build the pin's two-stage image, and the operator's shell has no image tooling. The image Render runs is the one CI qualified, published by digest:

1. **Qualify and export.** Dispatch `paperclip-image` by hand on the candidate's ref. Its qualification is the same as a pull request's, and its evidence artifact too. Only a run by hand, and only after its receipt reads `qualified`, also exports that exact image (`docker save`) as the artifact `paperclip-image-qualified-<run>-<attempt>`, kept 7 days, with its image ID checked against the run's identity record. A pull request's run exports nothing.
2. **Publish.** Dispatch `paperclip-image-publish` with that run's id and the candidate's full SHA (`candidate`). Dispatch itself needs write access. The job runs only when both the dispatcher and whoever triggered this attempt are the repository owner's account (`github.actor` and `github.triggering_actor`), so a re-run by anyone else does nothing. It builds nothing and qualifies nothing. It checks four things:
   - the run is a successful `paperclip-image` run by hand, and its head is exactly the named candidate: a run of any other commit is refused;
   - its receipt reads `qualified`, with every check passed, and names that run, its attempt, its head as the candidate, the pin, and the identity record's image ID on `linux/amd64`;
   - its identity record names its own head as a clean Sophia commit, the pin, and `linux/amd64`;
   - the export names the same image ID, commit and pin, its archive matches its SHA-256, and it loads with exactly that image ID.

   A receipt, record or export that names another run, attempt, commit, pin or image is refused; the unit tests hold a mutant of each field. Every value the workflow passes from one step to the next is checked against its form first.

   Then it pushes the image as `ghcr.io/davidelaverga/sophia-paperclip:sophia-<commit>-paperclip-<pin, 12>` and writes a delivery record: the digest, the image ID, the commit, the pin, the manifest's SHA-256, the qualified run, and whether an anonymous pull works. The record goes to the run's summary and to the artifact `paperclip-image-delivery-<run>`, kept 90 days.
3. **Run.** Render's Paperclip service uses `ghcr.io/davidelaverga/sophia-paperclip@sha256:<digest>` from that record: by digest, never by tag.

**Publication permissions and visibility.**
- The publish job holds `contents: read`, `actions: read` and `packages: write` through its own `GITHUB_TOKEN`, and uses no other secret. `packages: write` is this repository job's package permission: the platform does not limit it to one package. The workflow's commands name only `ghcr.io/davidelaverga/sophia-paperclip`, and the review of the workflow at the candidate is what holds it there.
- Its budget: 65 minutes for the job, above its steps' 52; the unit tests hold that sum.
- No Render, production or registry credential is created or used.
- The image holds only the build of the public Sophia and Paperclip sources and their defaults. The qualification's synthetic credentials are generated at run time and never built in. The service's own settings (§3) are given at run time on Render.
- The repository is public. The package must be **public** for Render to pull it without a registry credential. If the first publication leaves it private, which the delivery record's `anonymousPull: false` says, a maintainer sets **this one package's** visibility to Public once in its settings. Making it public needs no new credential. Then an anonymous pull of the record's digest must answer 200 (the workflow's last check, or the same request by hand) before Render is pointed at it.
- Published versions are immutable by digest. A version a service runs is never deleted.

This is the delivery step D4 needs. It is not hosted qualification: the instance's memory, disk, private network, SSH access and the fence after a deploy stay Codex's on the platform (CC-0009 §4).

### 2.2 SSH: the operator's key, its reach, and each image's precondition

- **The key (decision D-K1).** The dedicated ED25519 public key `SHA256:XRC1W85qFfkDDs82lNdtZ3grrUgRwzmUlbdd1lcQC+4`, named `sophia-joint-release-operator-20261009`, is registered on Render account `usr-d38p97gdl3ps73a64hjg` only once D-K1 approves it. - **Its reach is account-wide.** A key registered on a Render account reaches every service of that account that offers SSH, which excludes free services. It is not limited to one service.

  - the Paperclip service's operator path (CC-0009 §4): loopback, and the UI only through a localhost-only tunnel, `ssh -N -L 127.0.0.1:3100:127.0.0.1:3100 <the Connect address>`;
  - the render host's verification (§8).

  It is never used on the API or the runtime.
- **Retention.** The key is removed from the account at the end of the batch, or at the expiry D-K1 sets, whichever comes first. Its removal is recorded with the batch. The existing "Mem0 Codex key" is not this batch's to change.
- **What Render's SSH needs of each image.** The session runs as the image's user. Per Render's documentation (Docker-specific configuration, as Codex quoted it), the root account must not be locked, no persistent disk may be mounted at that user's `$HOME`, and the session's keys go in its `~/.ssh` at 0700.
  - **Both images run as root and set no `HOME`,** so it is `/root`, as root's passwd entry says. Both make `/root/.ssh` at 0700, and neither locks an account.
  - **Paperclip's disk is mounted at `/paperclip`, not at root's home.** Only the server, run as `node` by the pin's entrypoint, has `/paperclip` for its home, and `start.sh` sets it. Until this candidate, the image set `HOME=/paperclip` for every process, its user root's included, which put root's home on the disk.
  - **Root's shadow entry is `*` in both bases.** Read on 2026-10-09 from `node:24.21.0-bookworm-slim@sha256:0e0ff40c…` (render host) and `node:24-trixie-slim`, platform manifest `sha256:c83040f7…` (Paperclip). `*` is Debian's default: no password, and not the `!` prefix that `passwd -l` and `usermod -L` set. OpenSSH's own source defines the locked prefix for Linux as `!` (`configure.ac`, `LOCKED_PASSWD_PREFIX`; `platform.c` applies it and account expiry). Render's public documentation says only that root must not be locked, and does not say how its platform treats `*`. **Decision (Codex):** keep `*` and change no password. Only the hosted check on the final image decides (below). It comes before Paperclip is enrolled or any paid work starts. A refused session is a stop (§5).
  - **CI checks each built image** with `scripts/render-ssh-check.sh`, run inside the image as it starts:
    - the user is root;
    - `HOME` is `/root`, as in passwd, and for Paperclip not on `/paperclip`;
    - `/root/.ssh` is the user's own, at 0700;
    - root's shadow entry is neither `!`-locked nor empty.

    A failure fails the run, so the Paperclip image is neither exported nor published. The step is in `paperclip-image` and in `UML render host`.
  - **Hosted, separate from CI, before relying on it:** Codex checks the session on each instance, with the final image: `ssh <the Connect address> 'id -un; echo "$HOME"; ls -ld "$HOME/.ssh"'` must print `root`, `/root` and `drwx------`. CI shows what the image holds; only this shows what Render's session does with it.

The guard holds for this namespace only while **the deployed API is its one writer**:
- the bucket's settings and the project's one S3 key pair are held by the production API alone, whose login is `sophia-next`'s `sophia_api`;
- no other deployment, staging, local copy or database is given them;
- nothing is uploaded into the bucket from the dashboard.

A writer guarded by another database, or none, could replace an object here. Changing the bucket, endpoint or project after an output is stored is a stop (§5): stored sources would no longer read. The probe's first line names the namespace it wrote in, and it must be this one (§8).

**Write-once storage on the S3 key (P1, source-bound).** Supabase's S3 PutObject replaces an object and ignores `If-None-Match` (pinned upstream `307c5e31`, SDD-01-CX-0015). So the guarantee comes from the API, which is the only holder of the key:
- Before a byte is sent, `writeOnce` (`apps/api/src/byte-store.ts`) claims the key in `sophia.object_writes` (0044), in a transaction of its own that commits first.
- A key already claimed is refused with 409 before any I/O to the store. This covers this API, an instance racing it, and the same bytes again.
- A claim that cannot be made refuses the write.
- `buildApp` hands the routes no other store.
- An API with a store is not `/ready` without 0044.
- The keys are fresh besides, and every read checks the recorded SHA-256.

Shown on real PostgreSQL against a store that replaces as Supabase's does:
- a second write of other bytes, and of the same bytes, to a written key are refused, and the first bytes stay;
- eight racing writes of different bytes to one key over eight connections leave one write and its claim;
- three mutants fail those tests.

**Hosted proof: pending** until Codex runs §8's write-once probe on the deployed API, in this namespace: the same physical key, written again sequentially and concurrently, with one PUT reaching the provider.
