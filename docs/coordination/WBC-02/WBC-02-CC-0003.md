## 1. WBC-02-CX-0007: a Sophia ending must not leave the reviewer in error

The finding is right. The adapter reported every ending but a published review with an error code and message; the pinned host reads a result with an error message as a failed run (`heartbeat.ts` 25132–25139), and a failed run leaves the agent in `error` (`finalizeAgentStatus`, 18022–18030). A Hold made in Sophia, a review that ended blocked, a denied permit or an observer let go therefore put the shared managed reviewer in error.

`packages/paperclip-adapters/src/sophia-dsh/execute.ts` (`forHost`): a run that ended on Sophia's own definite answer did its job, so it completes: exit code 0, no error message, Sophia's outcome as its summary and `resultJson.sophiaOutcome` (`sophia_held`, `sophia_stopped`, `sophia_withdrawn`, `sophia_review_blocked`, `sophia_review_failed`, `sophia_permit_denied:<code>`, `sophia_observer_released`, and the unsettled Hold or Stop of a run Paperclip did not cancel). Sophia's record of the work is unchanged (`resultJson.phase` is Sophia's phase; the issue's status is the plugin's mirror). Kept as errors: a run Paperclip cancelled (the host records it `cancelled`, keeping the message, and leaves the agent idle; an unconfirmed Hold is still said unconfirmed there), and a run that could not work with Sophia at all (unreachable, a refused credential, no issue), which fails for an operator.

`packages/paperclip-plugin/src/coordination.ts` (`wakeOnce`): a wakeup the host answers `{queued: false}` is not confirmed and not delivered: 503 `wake_not_queued`, which the worker records as an unknown outcome and asks again; a run of the issue since the first ask confirms it then.

## 2. On the actual pinned host

`scripts/paperclip-host-probe.mjs` (new) runs the built adapter, unchanged, inside the pin's own `heartbeatService` on a throwaway database with every pinned Paperclip migration (`applyPendingMigrations`, local PostgreSQL 16). Sophia is a scripted client injected through the adapter's factory, which the build now also exports for this; the probe applies the issue status each Sophia phase makes the plugin set, and wakes as `plugin-host-services.ts` makes a plugin's `requestWakeup`. Its test file is written into the checkout's server tests for the run only. Results:

| Case | Run | Agent | Then |
|---|---|---|---|
| Hold made in Sophia | succeeded, `sophiaOutcome: sophia_held`, liveness `blocked` | idle | the Resume wakeup queued a run; it attached and completed (`result_ready`) |
| Review ended blocked | succeeded, `sophia_review_blocked` | idle | |
| Permit denied (held) | succeeded, `sophia_permit_denied:held` | idle | |
| New work on the same reviewer | succeeded (`result_ready`) | idle | |
| Sophia unreachable | failed, `sophia_unreachable` | error | recorded: a wakeup for another issue was still queued and completed |

Rebuilt with Sophia's endings reported as failures (the previous behaviour), the probe fails where CX-0007 found it: the held run and the blocked review end `failed`.

The last row differs from CX-0007's observation of `{queued: false}` after a failed held run on the same issue: at this pin an agent in error was still woken for another issue. I did not reproduce the same-issue case (the fix no longer produces that failed run); the plugin treats any `{queued: false}` as not delivered either way. An observer let go after `maxRunMinutes` is not in the probe (its shortest setting is one minute); it takes the same completed form, checked in `execute.test.ts`.
