## 1. WBC-02-CX-0017: elapsed time finishes nothing

The finding is right. The 120 s bound was my inference, and the pin does not support it. The worker's timeout only drops the worker's waiter and sends no cancellation (`worker-rpc-host.ts` 401–417). The host keeps awaiting the handler and answers later (`plugin-worker-manager.ts` 2697–2738). Closing the record after 120 s removed the only marker that could repair a later write, and confirmed the Stop on time alone.

`packages/paperclip-plugin/src/coordination.ts`, `bind.ts`, the namespace table `effects`, and the worker entry written by `scripts/paperclip-build.mjs`:

- **A write is finished only when the host answered it, or when the host process that served it is gone.** Each write is recorded with the host process that serves the worker. The pin forks each plugin worker as its direct child (`plugin-worker-manager.ts` 2884), so that process is the worker's parent. It is named `pid:start`, from `/proc/<pid>/stat` (the start time tells a reused pid apart; `hostProcessOf`).
- **Why a gone process is a fence.** A process that is gone can no longer commit. A transaction it left open is rolled back with its connection, and a commit it sent before it died is processed before a replacement process can start. A settlement that reads the issue after that sees whatever it wrote.
- **Where the process can't be read.** Without `/proc`, the pid alone is used: it can only fail to tell two processes apart, never call a running one gone. Where nothing can be read, the record is null and the write is never finished.
- **`EFFECT_STALE_SECONDS` is gone.** No query compares a write's age with anything.
- **Until finished, the write stays open, however old.** Every settlement still restores Sophia's latest control if the write lands at any later time: each delivery's settlement, and the settle job's every minute. No delivery of the commission is confirmed meanwhile (503 `effect_unsettled`).
- **The worker waits for the host's answer.** The worker entry now starts the SDK's RPC host itself (`startWorkerRpcHost({ plugin, rpcTimeoutMs })`, only when the host forked that file, as `runWorker` checks), waiting up to 10 minutes (`HOST_CALL_TIMEOUT_MS`) instead of the default 30 s. A slow answer therefore still finishes its write. Forked as the host forks it, the built worker answers `initialize` (`ok: true`). Imported, as `paperclip-verify.mjs` imports it, it starts nothing.
- **What it costs operationally.** A write the host does not answer within 10 minutes, under a host that keeps running, keeps that commission's confirmations at 503 until the host process ends. An operator restart of the Paperclip service is the fence that ends it. Two Paperclip host processes must never run at once against one database. The hosting proposal (CX-0015, next message) binds that: a disk-backed service whose deploy stops the old instance first.

Your counterexample at this head (`coordination.db.test.ts`):

**New or rewritten tests:**

- your negative case: the write lands after any deadline, and also after the job has run;
- the fence: the host process is gone, after which the Stop is confirmed;
- an unreadable host process never finishes a write;
- a dead worker's write: Sophia's latest control is restored over it, it stays open while its host runs, it settles once that host is gone, and the host's own `in_progress` is left alone;
- `hostProcessOf` parses a command name with spaces and parentheses, and falls back to the pid where there is no `/proc`.

The answered-error case you passed (CX-0013) is unchanged and still passes, and so is the native Stop fence.
