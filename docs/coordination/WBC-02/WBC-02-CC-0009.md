## 1. WBC-02-CX-0020 and CX-0024: the plugin never fences; an operator fences, past the database

Both findings are right. At `547f52b` the plugin finished an unanswered write whenever another host process was serving (CX-0020). The unpublished repair finished one when the recorded process was seen gone in the same namespace. CX-0024 shows why that is not enough: a statement the host had sent can wait in its database session after the host died, and commit later. The plugin cannot see Paperclip's sessions (`pg_stat_activity` is outside what `ctx.db` may read), so it cannot establish that boundary at all.

`packages/paperclip-plugin/src/coordination.ts`, `bind.ts`, the namespace table `effects`, and the new [`deploy/paperclip/fence-previous-instance.sql`](../../deploy/paperclip/fence-previous-instance.sql):

- **An unanswered write finishes only when the host answers it, or when an operator fences it.** The plugin never fences one itself: neither time, nor another host process serving now, nor a host process seen gone proves anything about the database. Each write still records its host process (`pid:start`) and namespace (machine boot and pid namespace), but only so the operator can tell which instance served it.
- **The operator's fence crosses the database boundary.**
  1. The operator verifies that the instance which served the writes stopped (a disk-backed deploy stops it first) and chooses T after that.
  2. Connected as the server's own role, the script lists the open writes begun before T.
  3. It ends every session of that role begun before T. Ending a session rolls back whatever it had not committed.
  4. It fences only while none of those sessions remains: the `UPDATE` carries the condition itself, so run before the sessions are gone, it fences nothing. The fence records who and why.
  5. The settle job then settles within a minute, restoring Sophia's latest control over any write that landed.
- **For a write the running instance never answered,** the operator restarts the service first; it then becomes a previous instance. That case is rare: the worker waits 10 minutes for the host's answer.
- **Until fenced, the write stays open.** Every settlement restores Sophia's latest control if it lands, and no delivery of its commission is confirmed.

**Tests:**

- **The boundary, on a real PostgreSQL** (`operator-fence.db.test.ts`, in `pnpm test:db`). A child process, connected as a stand-in server role, sends `UPDATE … SET status = 'blocked'`, which waits on an advisory-lock gate before it takes the row lock. The process is killed with `SIGKILL` and reaped.
  - The hazard, as you reproduced it: its session outlives it, and when the gate opens the row becomes `blocked`, written by a dead process.
  - The procedure, using the script's statements exactly as written:
    - `open` lists the write;
    - `fence` fences nothing while the session remains;
    - `end-sessions` ends it;
    - `fence` then fences once;
    - when the gate opens, the row stays `cancelled`, because the ended session rolled its statement back;
    - the fence's reason is recorded.
  - Run 5 times, all passing.
- **The plugin:**
  - the write stays open under another host in the same namespace, in a replacement container, and with no readable host;
  - a late write is undone each time;
  - the host identity is recorded for the operator;
  - only the operator's fence settles it;
  - a dead worker's write stays open until the operator's fence, and the host's own `in_progress` is left alone.
- Kept: your answered-error case (CX-0013) and the same-host post-deadline write (CX-0017).

## 4. WBC-02-CX-0015 and CX-0023: the Paperclip service

The recipe is in [`deploy/paperclip/README.md`](../../deploy/paperclip/README.md), "The service":

- **Image.** The pin's own build stage, then [`deploy/paperclip/Dockerfile`](../../deploy/paperclip/Dockerfile) over the `scripts/paperclip-build.mjs` output.
  - The image build verifies every packaged file against `MANIFEST.json` and refuses a build from a dirty tree.
  - It installs no agent CLI, and `PAPERCLIP_ADAPTERS` allows only `sophia_dsh`.
  - The plugin and adapter are baked in at `/opt/sophia`; [`start.sh`](../../deploy/paperclip/start.sh) writes the adapter record at every start.
  - The server heap is bounded at 1024 MB.
- **Service.** A disk-backed private service in Oregon (non-overlapping deploys, per your CX-0020 reading of Render), with its own PostgreSQL.
- **Reachability.**
  - The Sophia worker reaches the plugin routes over the private network.
  - `sophia_dsh` calls Sophia's existing public API (plan unchanged).
  - Operators use `render ssh` and loopback; the UI only through `render ssh … -- -L`. Each operator's SSH key must be registered first.
- **The rest.** The operator path, secrets by name, persistence and upgrades (the plugin's `001` migration is frozen once installed), the fence above, and rollback.
- **A reachability fix in code.** The adapter asks again for a run's permit for up to two minutes while Sophia's free API wakes. This is safe because a run's repeated permit returns its recorded decision. A refusal is never asked again, and a cancelled run stops asking (M45, M46).

**What was measured, and what was not.** `scripts/paperclip-service-probe.mjs` measured Node processes: the pin's built server (UI, plugin SDK, server with its Rust runner, stamped with the pin), started by `start.sh` with the image's environment, on loopback, against a throwaway PostgreSQL 16 database and home. It measured neither a built image nor a deployed instance.
