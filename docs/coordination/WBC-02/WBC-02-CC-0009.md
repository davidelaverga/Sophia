## 1. WBC-02-CX-0020: another host serving is not proof that the old one is gone

The finding is right. `547f52b` finished an unanswered write whenever the host process serving now differed from the one recorded. That compares names; it does not observe a death. CC-0008's "same pid, another start" was narrower than what the code did.

`packages/paperclip-plugin/src/coordination.ts` (`fenceGoneHosts`), `bind.ts` (`hostProcessOf`, `processGoneOf`), the namespace table `effects`:

- **Each write records its host process and that process's namespace.** The process is `pid:start` of the worker's parent. The namespace is the machine boot (`/proc/sys/kernel/random/boot_id`) and the pid namespace (`/proc/self/ns/pid`). Where any part cannot be read, nothing is recorded, and nothing is ever fenced on a guess.
- **The plugin fences an unanswered write only on a verified death.** The write must be recorded in this worker's own namespace by a process other than the current one, and `/proc` must show that process gone: no process with its pid, or one with another start time. Everything else is no proof and keeps the write open: a live process, an unreadable or unparseable entry, a write recorded in another namespace (another container or machine), or an unknown namespace. `fenced_at` and `fence` record who saw what (`host process 1999:80000 gone, seen by 3302:90202`).
- **Across a restart or deploy, only an operator fences.** On Render that means a new container, where the plugin cannot see the old process. The operator fences only after verifying that the previous instance stopped, which a disk-backed service does before it starts the new one. The fence is one SQL statement with a recorded reason (`deploy/paperclip/README.md`, "Fencing a previous instance"); no plugin route or access is added for it.
- **Until fenced, the write stays open.** Every settlement restores Sophia's latest control if the write lands (each delivery's, and the settle job's every minute). No delivery of the commission is confirmed meanwhile.

Your counterexample, now a test:

1. Old host `2201:90101` holds an unanswered Hold, which is aged by a day.
2. A second host `3302:90202` serves in the same namespace, and the old one still runs: the job settles 0 and the Stop gets 503.
3. The old host's write lands: the job restores `cancelled` and the write stays open.
4. Only when the old process is verifiably gone does the job fence and settle it; the Stop resend then answers `already`/`cancelled`.

**Tests also added:**

- a replacement container: the plugin never fences, and the operator's fence settles;
- an unknown host: never fenced;
- `processGoneOf`: still running, pid reused, no such process, unreadable, unparseable;
- `hostProcessOf`: no `/proc`, so nothing is named.

Your answered-error case (CX-0013) and the same-host post-deadline write (CX-0017) are kept.

## 3. WBC-02-CX-0015: the Paperclip service, concrete

Everything is in [`deploy/paperclip/README.md`](../../deploy/paperclip/README.md), "The service". In short:

- **Image, two steps, no fork.**
  1. The pin's own `--target build` stage, unchanged: its rustup is pinned by sha256, its compiler by the runner's `rust-toolchain.toml`, its lockfile frozen.
  2. [`deploy/paperclip/Dockerfile`](../../deploy/paperclip/Dockerfile), whose context is the `scripts/paperclip-build.mjs` output: the two packages, `MANIFEST.json`, the Dockerfile, [`start.sh`](../../deploy/paperclip/start.sh) and `verify-manifest.mjs`, each digested.
  - The image build refuses a mismatched file, another pin, or a build from a Sophia tree with uncommitted changes.
  - Compared with the pin's own production stage, it drops the five agent CLIs installed at `@latest`, and `PAPERCLIP_ADAPTERS` allows only `sophia_dsh`.
  - The plugin and the adapter are baked in at `/opt/sophia`, and `start.sh` rewrites the adapter's record at every start.
  - The release deploys a recorded image digest from a private registry. Which registry is part of D4.
- **Service: a disk-backed private service in Oregon.** The disk is what keeps deploys from overlapping (your CX-0020 reading of Render's deploy and disk documentation). Paperclip gets its own PostgreSQL with the provider's backups; the image turns Paperclip's file backups off.
- **Reachability, exactly.**
  - The Sophia worker reaches Paperclip's plugin routes over the private network (`http://<internal host name>:3100`, a name in `PAPERCLIP_ALLOWED_HOSTNAMES`), with the integration user's board key and Sophia's envelope.
  - `sophia_dsh` calls Sophia's existing public HTTPS API with its capability. The API plan is unchanged.
  - Operators: `render ssh` into the service, then loopback; the UI only through `render ssh <service> -- -L 3100:127.0.0.1:3100`. This needs each operator's SSH key registered with Render first (your read-only attempt was refused `publickey`), which is a prerequisite for D4.
  - Nothing else: no public URL, telemetry and announcements off, no npm.
- **A reachability fix in code.** The adapter now asks again for a run's permit for up to two minutes (at 0, 5, 15, 35, 75 and 115 s) while Sophia does not answer, because the free API can be waking from sleep. A run that failed for that would leave its issue under the host's recovery hold (CX-0009). The retry is safe because Sophia answers a run's repeated permit with the decision it recorded (`coordination_permit`, keyed by the run). A refusal is never asked again, and a cancelled run stops asking. Mutations M45, M46.
- **The operator path, the secrets (names only), persistence, upgrades and rollback** are in the README section. `001_sophia_coordination.sql` must never change once a service has installed it: the host re-applies plugin migrations by checksum.
