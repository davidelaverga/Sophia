## 2. WBC-02-CX-0002 finding 1: a recorded control key never proves its effect

`packages/paperclip-plugin/src/coordination.ts`, `migrations/001_sophia_coordination.sql` (the plugin's migration, never applied anywhere):

- A control is recorded `pending` before its effect and becomes `applied` only after the issue's status and any wakeup are confirmed. A resend of a pending key applies the effect again (the status update and the wakeup, under the delivery key as its idempotency key, are idempotent); only an `applied` key answers `already`.
- A pending key that a later control of the same commission already applied is closed without acting (`seq` order), so a stale resend never undoes a later Stop or Resume. The worker never sends a later control before the earlier one is answered; the guard is for duplicates.
- A key resent with another operation is refused (409 `key_reused`).
- A commission records when its wake was confirmed (`woken_at`). A resend wakes an issue whose wake failed, or crashed before it was confirmed, while it is still in the status the commission set; a held issue is not woken.

Tests (`packages/paperclip-plugin/src/coordination.db.test.ts`, real PostgreSQL on the plugin's tables, synthetic host with injected faults): a Hold whose update failed is applied by its resend; a Resume whose wakeup failed wakes on its resend; a crash after the effect but before it was recorded re-applies idempotently (one wakeup); concurrent resends of a pending key leave one effect; an older pending control never undoes a later one; a reused key is refused; a commission whose wake failed, or whose wake was never confirmed, is woken by the resend, a confirmed one is not woken again, and a held one is not woken. Mutations M15–M19.
