## 2. WBC-02-CX-0002 finding 1 and WBC-02-CX-0004: a key never proves its effect, and a wakeup is never asked blindly

`packages/paperclip-plugin/src/coordination.ts`, `migrations/001_sophia_coordination.sql` (the plugin's migration, applied nowhere), `manifest.ts` (`coreReadTables` gains `heartbeat_runs`):

- A control is recorded `pending` before its effect and becomes `applied` only once the issue's status and any wakeup are confirmed. A resend of a pending key applies it again; only an `applied` key answers `already`. A pending key that a later control of the same commission already applied is closed without acting (`seq`); a key resent with another operation is refused (409 `key_reused`).
- CX-0004 is right that the synthetic host's key deduplication proved nothing. What the pin does, read from its source: the host passes the key to `heartbeat.wakeup` and then writes its activity log, so a call can fail after the wakeup is durable (`plugin-host-services.ts` 2164–2228); the generic issue path inserts a fresh wakeup request with no deduplication by the key (`heartbeat.ts` ~28373); a wakeup while a run of the issue is active is coalesced or deferred behind it (~28121–28178). So the plugin never relies on deduplication. Every wakeup (a commission's, a Resume's) goes through `wakeOnce`: the ask is recorded before it is made; a resend that finds it unconfirmed looks for a run of the issue since the first ask in `public.heartbeat_runs` (a core table plugins may read) and, if there is one, confirms it without asking; while the ask may still be in flight it answers 503 `wake_in_progress` (the worker retries later); only a stale ask with no run since is asked again, claimed by exactly one resend. A second run would still only attach to Sophia's one attempt (M06); this keeps the host from being asked for one.
- CX-0004 also surfaced a defect of mine: the first repair read its control row with `INSERT … RETURNING` through `ctx.db.query`, which the pin refuses (SELECT only). All plugin SQL now keeps to the pin's rules: reads are SELECT through `query`, writes are namespace-only through `execute`. The synthetic host applies those rules (`host-sql.ts`, unit-tested), and `scripts/paperclip-verify.mjs` now runs the pin's own `validatePluginRuntimeQuery`/`validatePluginRuntimeExecute` over every statement the built worker sends (7 queries, 22 executes) and `validatePluginMigrationStatement` over the migration. It needs the pin's db package built (`pnpm --filter @paperclipai/db build`) besides its SDK.

Tests (`coordination.db.test.ts`, real PostgreSQL; the synthetic host now follows the pin: no deduplication by key, every arrival queues a run in a stub `heartbeat_runs`, and a fault fails a wakeup before it is durable or after): a Hold whose update failed is applied by its resend; a Resume or commission wakeup that never arrived is waited for while in flight, then asked once when stale; one durable but unanswered is confirmed by its run, with no second run; concurrent resends of a stale ask make one run; a crash between the effect and its record re-applies without a second run; a commission held since its create is not woken; an older pending control never undoes a later one; a reused key is refused. Each asserts the runs the host queued. Mutations M15–M22.

Not claimed: these semantics are the pin's source, not a running host. A run since the first ask confirms a wakeup even if another trigger started it (it ran the issue); a deferred wakeup has no run yet, so it is asked again once stale and the host merges an issue's deferred wakeups. The live checks should include a Resume whose plugin reply is lost and a stale ask during a deferral.
