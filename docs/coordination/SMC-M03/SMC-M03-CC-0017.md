### Why it is blocked

- **Capacity.**
  - The 384 MiB acceptance fails in every combined run, and enforcing it thrashes.
  - `nice` brings no benefit: one CPU quota covers both.
  - Memory follows layout, not bytes, so the 8 MiB input bound bounds nothing.
  - No instance size prints every legal draft, so a PDF needs admission by structure (pages, table cells) on any host.
- **No hard boundary for the render.** Only a delegated sub-cgroup bounds a render, and whether Render allows one is unknown. The other levers do not hold:
  - `oom_score_adj` is not pinned without CAP_SYS_RESOURCE (the render uid can lower it, and Chromium lowers its renderer to 300);
  - the browser can fill the shared `/dev/shm`, and those pages outlive the render;
  - RLIMIT_DATA works per process only.
- **Isolation.** The reviewed layout runs the supervisor and the kernel as root. In the runtime's container:
  - root with Docker's default capabilities reads other root processes' environments, including PID 1's, which holds every injected secret;
  - job directories (0755/0644) are readable by the runtime's uid;
  - one boundary would hold the provider keys, every project's `/var/data` and the cross-project runner capability.

  The fixes change the reviewed kernel files, which changes the kernel identity and couples renderer releases to runtime redeploys.
- **Platform, for the hosted probe.**
  - Does a Render Docker service run as root with CAP_SETUID and CAP_SETGID?
  - Can it mount a fresh `/proc`? Any `/proc` mask refuses `--mount-proc`; reproduced locally.
  - Does a memory-cgroup OOM kill the whole instance (`memory.oom.group`)?
  - Does `/var/data` keep its ownership across the native-to-Docker change?
