## What works

- `GET /api/v1/projects/{id}/snapshot`: consistent snapshot and cursor in one REPEATABLE READ READ ONLY transaction under the verified actor. Members get identical snapshots; outsiders and unknown projects get 403.
- `POST /api/v1/projects/{id}/commands`: `sophia.admit_goal_command` with `Idempotency-Key`. Returns 202 and a receipt. The same key and payload return the same receipt; a different payload returns 409 `idempotency_conflict`; a stale revision returns 409 `stale_revision`; viewers and outsiders get 403. Unknown fields such as `actorId` are rejected (422), not silently stripped. A failure during COMMIT returns 503 `retry: same_admission_key`.
- `GET /api/v1/projects/{id}/events?after=N`: authorized replay, then a live tail woken by `LISTEN/NOTIFY` (migration 0005, fired on commit only) with a re-read fallback on every heartbeat (10 s since the addendum). SSE `id` is the decimal sequence. Hidden events become `cursor.advanced`. Membership is rechecked on every read, and revocation ends the stream.
- `/ready` refuses a migration-owner, superuser or BYPASSRLS login and checks the required functions.

## Addendum: idempotent `createProject` (same day, same attempt)

**Problem:** the contract requires `Idempotency-Key` on `POST /api/v1/projects`, but the pack's `sophia.create_project(text)` has no idempotency, so a retry after a lost reply would create a second project. Command keys are scoped to a project and cannot cover creation.

**Change:** migration `0006_idempotent_project_creation.sql`.
- A `project_creations` register keyed by `(actor_id, idempotency_key)`, with RLS enabled and no grants.
- A new `sophia.create_project(title, key)`. It claims the key with `INSERT … ON CONFLICT DO NOTHING`: a concurrent duplicate waits on the primary key, then returns the receipt if the first committed, or creates the project if the first rolled back.
- `EXECUTE` on the old `create_project(text)` is revoked from `sophia_api`. Pack migrations stay verbatim and forward-only.
- Route `apps/api/src/routes/projects.ts` (the destination in `route-bindings.json`) returns 201 `ProjectCreated`.
- `/ready` also requires the new function.

## Addendum: the db README race suite (same day, same attempt)

`packages/persistence/src/races.db.test.ts` covers every item left in the pack's "Before declaring S1-02 complete…" list. It uses a real `sophia_worker` login next to `sophia_api`.

**First run, against migrations 0001–0006: 7 of 12 failed, all as predicted before writing the tests.**

| Failure | Cause | Fix |
|---|---|---|
| A queued `steer` whose brief source was withdrawn was still claimed | **Bug in the pack's `claim_outbox`**: it never rechecked the body source, contradicting the pack's own reference rule ("revoked source … denies even a fresh queued dispatch") | 0007 replaces `claim_outbox`: non-cleanup rows also need an eligible, project-scoped, ready body source |
| A `steer` admitted while an **unlocked** withdrawal was committing was dispatched | same | same |
| Three lease tests | no primitive recorded a dispatch outcome under its lease, so nothing could fence a worker whose lease had expired | 0007 adds `record_dispatch_result(project, outbox, lease_token, result)`: live token only, one write only; an expired lease records `outcome_unknown` |
| Competing publishers → `invalid_state` | "Stable head changed" was misclassified | `classifyDbError`: CAS losers → `stale_revision` |
| Another project's candidate → `invalid_request` | "Candidate not found" was misclassified | `…not found` → `not_found` |

**After the fix: 12/12. Full DB suite 44/44, three consecutive runs.**

| Pack item | What the test proves |
|---|---|
| Two competing publishers | two connections; the second is **verified blocked** on the project lock and then loses with `stale_revision`; the stable head is the winner; republishing against the head it now sees succeeds (a real CAS) |
| Cross-project composite FK | another project's goal → `not_found`; its brief source → `source_ineligible`; its candidate → `not_found`; the schema rejects mixed-project rows even for the migration owner (`23503` on `outbox` and `work_attempts`) |
| Lease expiry during an actual HTTP call | a local HTTP server answers after 6.5 s; the claim holds a 5 s lease; the sweeper turns the row into `outcome_unknown` (not `pending`); a new claim does not pick it up again; the late `acknowledged` is refused and the row stays `outcome_unknown` |
| Grant revocation while queued | a revoked author's queued review is not claimed, and is claimed again once the grant is restored (control). A revoked author's Stop is still dispatched: cleanup is never blocked |
| Source-withdrawal races | queued, and admitted during an unlocked withdrawal: never dispatched. A withdrawal that takes the project lock first: the admission is **verified blocked**, then fails `source_ineligible` |
| (already covered) duplicate writes, denied DML, pool actor leakage | persistence suite |
| Roles | the API login cannot call worker functions (`forbidden`) |

**Also fixed (test infrastructure):** test files migrate in parallel, and migration 0002's `IF NOT EXISTS … CREATE ROLE` raced across them (`pg_authid_rolname_index`). Migrations in `createTestDatabase` are now serialized with an advisory lock. Production runs migrations once.

### Still open, stated plainly

- **Claim vs. an uncommitted withdrawal.** `claim_outbox` reads eligibility without locking the source. A claim that runs while a withdrawal is still uncommitted can pass. Closing it takes two things. First, the dispatcher (S1-03/S1-09) must recheck eligibility at effect time, as architecture 12 already requires ("recheck at effect dispatch"). Second, every withdrawal or Forget handler must take the project lock first, as the lock-order test shows.
- Rows skipped for revocation or withdrawal stay `pending`. A handler that marks them `denied` with a visible reason is product work (membership and Forget handlers).
- Publication emits no project event: the SQL primitive does not, and the HTTP publish handler that must add it in the same transaction belongs to S1-07.
