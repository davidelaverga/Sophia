2. Record exact source commit/tree, built artifact identities, migration set, desired feature state, current app/API/runtime and rollback capability. Identify whether the change touches a combined runtime with other lanes' additions.

## Failure and stop rules

Stop the affected rollout on cross-project disclosure, missing/duplicated admitted text, false reply settlement, reappearance of withdrawn content, unbounded retries/spend, corrupted runtime identity or blocked control/erasure. Record the actual boundary and preserve evidence. Do not mask it by flipping every feature off, changing the model, using a more privileged account or rerunning until a prettier answer appears.

An unavailable provider, route or live test permission can leave the source release-ready but unqualified. Tell Davide which capability remains unavailable. Do not label a stub as a live provider and do not invent a schedule to return later.

## Rollback

Prefer first disabling new reply admissions and, if necessary, new text writes for the cohort, while retaining current authorized reads, privacy controls, pending-operation observation and stored content. Existing asks must be settled/cancelled or reconciled; disabling the UI is not cancellation.

Keep additive data and compatibility readers. Do not drop conversation tables or restore an old runtime that cannot enforce erasure merely to revert the feature. If the previous application cannot safely read the new records, retain the qualified read/erase API and hide only the unsupported front-end surface until an explicit migration is reviewed.

A rollback must not resurrect withdrawn text or replay old requests. Track backup/retention limits honestly. New execution under an older code version still requires the current permission, source eligibility and allowance. Re-enable only after the correction's affected gates are independently rerun.
