## What works

A member who can edit opens **Tasks**, presses **Review sources** under a goal, chooses one to three report versions (at most 32 KiB of text), an allowance within the project's cap and an optional purpose, and proposes. Sophia records one deterministic plan (`sophia.work.plan.v2`) and one admission decision for the proposer; nothing runs. The proposer starts it (**Start the review**). In one transaction Sophia admits one work item with its assignment, a hidden execution goal (the review's own Hold/Resume/Stop fence), an allowance on the shared research accounting, and one commission. The worker delivers the commission to the `sophia.coordination` plugin under an Ed25519 envelope; the plugin creates **one** core issue in the mapped Paperclip project, assigned to the managed `source-reviewer` agent, and wakes it. Paperclip's run calls the external `sophia_dsh` adapter, which opts into cancellation, asks Sophia for an effect permit, dispatches, and asks Sophia to start the work's one attempt through Sophia's existing native path. The runtime runs `sophia-source-review-v1` on `source-review-luna-high-v1` with three tools only (`read_review_source`, `submit_source_review`, `report_review_blocker`); every model call is reserved and settled against the work's allowance, eight at most. A finding may cite only a source a page of which reached the model: each page carries a receipt, kept by Sophia only as its hash, and the submission presents the receipts it rests on (Codex on #107). The review is published as an immutable source with structural checks (five sections, findings that cite only manifest sources this attempt read). The board shows it Complete with its result openable at its exact version; Paperclip's issue is mirrored `done`; the run reports its own usage (`per_run`; an uncertain cost is `null`). An adverse review is a completed review: the reviewed goal is untouched.

Hold, Resume and Stop from the board fence the runtime at once and are mirrored onto the issue; a cancelled Paperclip run holds the work (never stops or loses it); a lost commission reply is reconciled by its key; a withdrawn input stops the work and withdraws its result; a turn that ends without a result is nudged once, then the work fails with `no_result_submitted`.

## Not done, or known limits

- Nothing live (INT-01 live, INT-12 outage, INT-19, INT-20).
- After a run that genuinely fails (Sophia unreachable, a refused credential), the pinned host places a recovery hold on that issue (`issue_recovery_actions`, `legacy_execution_requires_reconciliation`), so its next wakeup is not queued (CX-0009). The plugin answers that as 503 `wake_not_queued` and the worker keeps asking; Sophia's board shows the delivery unconfirmed until an operator resolves the hold in Paperclip. The plugin never clears it, and never resets the agent.
- Run by Codex, not here: the installed plugin worker behind the host's authenticated HTTP routes, with a separate operator and a non-admin integration principal, passed at `414924f` (WBC-02-CX-0014: install, configure, disable and enable; forged and wrong-principal envelopes refused; one issue per commission; a signed Stop; refusal after membership revocation). The settle job added since (WBC-02-CX-0013) is checked under the pin's harness and its manifest under the pin's loader; its schedule in a running host is for Codex's next installed run.
- A write the host never answered within 10 minutes, or whose worker died, stays open until it is fenced, however long that takes.
  - The settle job and every delivery still restore Sophia's latest control whenever such a write lands.
  - Every delivery of that commission is answered 503 `effect_unsettled` (and the worker asks again) until the fence.
  - Only an operator fences, with `deploy/paperclip/fence-previous-instance.sql`, after verifying that the instance that served it stopped. The script ends that instance's database sessions first and fences only once none remains (WBC-02-CX-0024). For a write the running instance never answered, the operator restarts the service first.
  - A write the host answered, with an error included, is settled at once.
  - Two Paperclip host processes must never run at once on one database: the service is disk-backed, so a deploy stops the old one before the new one starts.
- Only status writes are settled. A wakeup asked late (after a Stop) can still queue a run; Sophia's permit then denies it (`sophia_permit_denied`), which ends the run as completed, so the fence, not the issue, keeps the work stopped.
- The pin's wakeup semantics are read from its source, not exercised against a running host (the SDK harness ignores the key). The plugin therefore never relies on deduplication: a run of the issue since the first ask confirms a wakeup, even one started by another trigger (it ran the issue, which is what the wakeup is for); a wakeup the host deferred has no run yet, so it is asked again only once stale, and the host merges an issue's deferred wakeups into its next run. Codex's live checks should include a Resume whose plugin reply is lost (one run) and a stale ask during a deferral.
- A status change made by a person on the Paperclip issue is not mirrored back: Sophia is authoritative, and its next control sets the issue again.
- Guidance and Ask stay unavailable (later missions).
- The board serializer exception: the board and receipt routes bypass `fast-json-stringify` after checking against the contract.
