## 3. Can Sophia connect existing ChatGPT and Claude projects?

### 3.1 Answer: useful continuity now; distinguish the kind of connection

The following are different product objects:

1. A ChatGPT Project containing chats, files and instructions.
2. A Claude.ai Project containing conversations and project knowledge.
3. A local Claude Code or Codex repository/worktree and its sessions.
4. A vendor-hosted coding project and its cloud threads.
5. An API-platform project used for billing, keys or organizational access.

A subscription to a coding product does not make all of those objects available through the coding runtime. A normal model API key is not a general credential to enumerate personal chat-project history.

**Verified:** OpenAI documents a personal data-export route containing chat history and other account data. Anthropic documents exports of conversation and user data for individual Free/Pro/Max users. Project sharing is also documented, but sharing within a vendor application is not automatically a third-party synchronization API. [W1–W4]

**Not established:** a general personal-account API through which Sophia can enumerate, subscribe to and continuously control every ChatGPT or Claude Project. This is a bounded research finding, not a proof that no current or future such interface can exist.

Enterprise compliance access is an important exception to a blanket “no API” statement. OpenAI documents Project information in its Compliance API. Anthropic's Compliance API has eligible Enterprise access to content including projects, chats and files under a separate access-key model. Those products are not assumed to be available to the founders' personal subscriptions. [W1, W7]

### 3.2 What I would ship

**Snapshot intake:** owner-selected exports, conversations, instructions, project files and source links. Parse the real representation, preserve provenance, let the user choose what belongs in the team project, and report omissions. An export's published description does not guarantee complete project grouping, every uploaded asset or hidden memory.

**Linked local project:** repository, allowed working files, relevant `CLAUDE.md`/`AGENTS.md` and selected session/handoff. Resume or adopt through a supported native owner route where available. Do not copy opaque session databases into another vendor or crawl the owner's entire home directory.

**User-initiated handoff tool:** a small Sophia MCP capability available in a supported ChatGPT/Claude environment. The user asks to send selected context to Sophia; the tool writes to a specifically authorized Sophia project and returns a receipt. Official plugin/connector mechanisms make this a plausible integration path. It is an implementation proposal, not proof that the desired account configuration has already been tested. [W5, W6]

A tool can receive a generated handoff package without granting Sophia reverse access to the vendor's entire Project. The package should retain sources and coverage, not merely a confident summary. Ordinary files/import remain the fallback when that account cannot use a custom tool.

### 3.3 What not to promise

Do not label an imported snapshot “live sync.” Do not imply an individual shared-chat link carries every project file and instruction: OpenAI explicitly distinguishes that link from sharing the complete Project. [W1]

Do not use session-cookie extraction, private web endpoints or desktop scraping as the foundation of a commercial connector. Do not treat a generated “project summary” as complete memory or automatically accepted team decisions. Sharing source and authorizing execution are different actions.

The exact Claude Code cloud Projects documentation could not be fetched in this pass: repeated opens of `https://code.claude.com/docs/en/projects` returned an access/cache error. Earlier September research about that feature is retained as historical context, but its current API/sharing limits are **not re-certified here**. This does not block local repository/session linking or snapshot intake.

### 3.4 Intake semantics to preserve

An imported record needs origin, owner, capture time, stable source reference when present, parser version, hash and coverage. An old assistant recommendation remains a recommendation. An explicit user decision can be proposed for acceptance in the current project, with its original attribution.

A later snapshot can update evidence without silently overwriting a newer accepted decision. Deletion/Forget and private-to-project sharing must apply to derived summaries and future prompt construction as well as the uploaded original. A retained private URL alone does not prove its contents were retrieved.

## 4. Three engineers, two owners, one project lead

The actual first-release inventory is fixed: **Davide's Codex; Davide's Claude Code; Luis's Claude Code**. Older examples assigning Codex to Luis are illustrative and must not leak into implementation acceptance.

### 4.1 What is native and what is an adapter

Dsh supplies native local-team mailbox behavior: queued source first, target durability before acknowledgement, target-side message identity for deduplication, step-boundary steering, idle activation and cold resume. Its task DAG includes revision checks and dependency rules. These are concrete mechanisms worth reusing. [D1]

The three owner-operated coding sessions are not automatically members of that same process-local domain. They need a scoped bridge between Sophia's admitted team assignment and their actual runtime interfaces. “Native peer communication” here should mean **programmatic exchange through supported mechanisms**, not screenshots and clicks, and not a claim that every vendor implements a common protocol identically.

### 4.2 Omnigent is the primary execution bridge

The inspected host-launch path requires the caller to own the target host and to have the required ownership of the session. Shared read/edit visibility is not automatically permission to start a process on another person's machine. Keep that rule. [O1]

Owners initialize or admit their own resources through the supported route. Sophia can then steer within the explicit project/session grant and available adapter behavior. A logical coordinator-worker assignment need not mirror the platform's parent-child ownership tree.

The queue/steer design documents materially different delivery: Codex native uses `turn/steer`; Claude native sends input into its managed pane with best-effort timing. The document reports particular live verification, but this review did not repeat it on the founders' installed binaries. [O2]

A controlled native terminal-input bridge is less invasive than desktop screenshots, but still needs a scoped session and honest receipt. Do not rename “sent” as “incorporated.” Nor should Sophia inherit the donor UI's choice to hide the sent/consumed gap when the user's preservation request makes that gap relevant.

Claude's custom-channel interface is a further candidate for receiving asynchronous messages and replying through tools. It is explicitly a research-preview/custom-configuration path, with permission and admission requirements. Do not make its presence a universal installed-client assumption. [W9]

### 4.3 Do not add expensive hierarchy just to relay a question

A peer message can be routed by application code. It need not trigger the technical lead to paraphrase it. Routine transport acknowledgements should not generate acknowledgement conversations.

A worker may challenge a coordinator, both may initiate useful questions, and a coordinator may inspect a partial result before completion. The project technical lead still owns dependencies and acceptance. A native subtask marked complete cannot independently unlock a product goal whose evidence is missing.

The fresh Library mailbox v2 is a useful reminder: it changes Claude and Codex's local operational roles for a named new epoch without rewriting the old messages' meaning. Preserve that flexibility, session identity and explicit ownership. Do not adopt its particular models or $5 Voice Lab allowance as global Sophia policy. [P5]

### 4.4 Deployment without new connectors

Deferring management connectors does not mean uncoordinated production effects. Use the founders' existing approved engineering/deployment routes, but assign one release operator or serialized release window for a shared environment. Other agents can prepare changes, inspect evidence and request a deployment; they cannot all mutate the same production target because their local settings permit it.

Source worktrees do not isolate a shared database. If a deployment result is uncertain, reconcile actual state before repeating it. Subscription billing, API billing, host permissions and project authority remain separately accounted for. No silent payer switch is permitted.

## 5. The heartbeat should be a real review—but not an expensive polling swarm

Davide's idea is adopted: a timed review invokes the technical lead while relevant work is active, even before a sophisticated detector exists. The proposal in the plan is a configurable five-minute project heartbeat, plus immediate meaningful event triggers and **Review work progress**.

Three different mechanisms should remain separate:

- **Liveness:** software checks which host/session is reachable and how fresh observations are.
- **Peer communication:** relevant questions and evidence are delivered as promptly as the runtime supports.
- **Technical review:** the lead interprets actual progress and decides what response is warranted.

A five-minute heartbeat produces at most twelve scheduled project reviews per active hour, versus thirty-six if independently run over all three resources. This is arithmetic on a proposed interval, not a measured cost. One project review can inspect bounded deltas for all current goals. Record the actual model usage, review duration and any correction cost.

The lead may continue, request evidence, steer, prepare a fresh alignment brief, obtain independent review, propose/replan, or notify a named human. The new brief preserves completed work, earlier failed probes, actual evidence and unresolved obligations; it is not a generic “start again.”

Suppress redundant invocations while one review is running. Coalesce scheduled and event-driven causes; keep an explicit manual question. Wait states can back off while owner alerts remain live. A stale stream causes an observation gap, not an invented circling verdict. Stop invalidates old review actions and prevents an expired timer from reviving work.

All material decisions are recorded and visible. A routine “continue unchanged” can update the last-reviewed state without speaking or creating a new card. A project-scope change remains a proposal unless already within the authorized mandate. A reviewer does not obtain permission to weaken acceptance criteria.

Symphony is useful reading here for eligibility checks, reconciliation, bounded concurrent runs and recoverable workspaces. It is not a semantic progress detector or Sophia's mission model, and the plan does not add a second Symphony controller. [S1]

## 6. Prototype simulation is not agent replay

The dsh replay package is valuable: it runs a real agent loop against recorded model streams, without provider calls, and provides explicit overrides for failures, cancellation and hangs. It is intended for deterministic control/protocol/browser integration tests. [D2]

It does **not** generate a prototype, provide mocked application APIs, or prove that a new live model makes correct decisions. Its documented first-call-order binding also assumes sequential delegation; parallel siblings need a suitably keyed test arrangement rather than pretending a linear recording validates every race. [D2]

The product path is instead:

**Design reference → source-backed UI → explicit simulated services/states → local preview → exact handoff → integrated app → real checks.**

Sprint 1 can implement a small state picker and realistic fixtures directly. Luis gets a bounded source editor and rebuild/diff path; he is not reduced to commenting on an image. Selecting a direction pins assets and intent without deleting alternatives.

Sprint 2 adds scenario authoring, Storybook where useful, network mocks through MSW, and Playwright checks/traces. Storybook's play functions exercise interactions; MSW supplies controlled network behavior; Playwright records actual execution for inspection. Their roles differ from dsh replay. [W10–W12]

S1 review-to-steer captures the exact displayed candidate, target evidence and change/preserve intent. It does not promise that a natural-language worker will never touch an unrelated source. General transactionally enforced target edits arrive in S2. Source versioning, stable previews and honest failed-candidate behavior are not deferred.

## 7. Donor findings and adoption decisions

### 7.1 Buzz — communication and human-floor patterns, not another product substrate

**Read at `d01e5f82058463709a22e93bb4cd795da5f53e10`:** README, incoming-event/delegation portions of the base prompt, ACP client lifecycle, and human-floor implementation; targeted search for steering and reported communication loops. [B1–B4]

Buzz treats people and agents as identity-bearing participants in a signed event system. Its contribution for Sophia is the separation between current request and prior context, exact destinations and callback identity, publishable results, and suppression of empty acknowledgement loops. A signed event establishes attributable authorship—not that the content is true. [B1, B2]

Its human-floor code has a generation/authorization mechanism that distinguishes local and remote human speech and can invalidate stale agent playback. This is a useful design reference for voice interruption. It is not a drop-in browser Google Live room: the inspected implementation belongs to Buzz's desktop playback environment. [B4]

Its ACP steering includes a negotiated `_session/steering` extension. The method name should not be treated as universally supported ACP. [B3]

The README itself places workflow approval glue and huddle lifecycle work in the “being wired up” category and push notifications in future intent. This is why the plan does not borrow Buzz wholesale for mobile approvals. [B1]

**Disposition:** adapt attributed event/recipient handling, response discipline and floor/playback ideas; use tested code only where separable and licensed. Do not deploy Buzz's relay/forge/identity platform solely to communicate with Sophia's three existing engineers. Keep one Sophia-facing identity.

### 7.2 QM — scope, durable mail, and a real distinction between delivery and wake

**Read at `861af65d75a1896418f8e1c7542b2ed34506324d`:** README, persistent-subagent documentation, harness input/result interfaces and sharing-access implementation. [Q1–Q4]

Its scoped workspace approach is relevant: audience, personal/shared resources, source scope, permissions and running context are separate inputs. Its turn interface carries structured approvals, silence and runtime choice rather than forcing every operation to appear as a chat sentence. [Q1, Q3]

The persistent-subagent contract is especially useful. `send_message` inserts attributed data durably **without starting a turn**. Delivery occurs at tool boundaries. `followup_task` explicitly queues work, and selected completion wakes depend on the `responsive_spine` path. Both persistent-subagent/spine features are opt-in. Simply copying the mailbox would not give Sophia automatic live dialogue with idle peers. [Q2]

QM also checks scope, audience and participant access. But its optional “open” sharing posture can deliberately bring eligible personal resources into shared work. Sophia should retain its stricter explicit project-release default. Read-only, background and live-human turns must not silently borrow one another's authority. [Q1, Q4]

Its harness interface contains provider-specific authentication fields. That is evidence of an integration model, not a reason to copy provider-token custody into Sophia. The current plan remains owner-native authentication for the contributed coding routes. [Q3, W13]

**Disposition:** borrow typed scope/turn/approval and durable delivery/recovery patterns. Do not adopt QM as the project platform, its vendor-auth implementation, or its broad open-sharing policy. Dsh remains the core; no second PM loop is added.

## 8. UI semantics recovered from the Library

The Studio specification is detailed enough to prevent a generic agent dashboard if used faithfully. Its strongest requirements are source-backed prototypes, executable handoffs and continuity across local lenses. [P2, P3]

**View, focus, discussion and action differ.** A person can inspect a reference without retasking the worker or forcing everyone into the same lens. One clear authorized request can still perform several necessary semantic operations; the design does not require five confirmation clicks. [P4]

**Attention is not blocking.** A milestone worth reviewing can produce an optional invitation with an authorized no-response continuation. A permission dependency remains unresolved even if its card is dismissed. Required controls remain reachable regardless of the discretionary card limit. [P2, P4]

**One underlying item, several views.** The same human action appears in Studio, Work, Activity and the return view. Native resolution retires that exact pending item; it does not create a new completed card while leaving the old one unresolved. [P2]

**Receipt stages remain honest.** Recorded, sent/provider accepted, incorporation observed and checked are different. The UI uses the best available evidence and explicitly states when a route cannot expose an intermediate stage. [P2]

**The artifact remains central.** Use the established dark/violet visual system and room anatomy as a design reference, not as an instruction to copy every sidebar or fixture controller. Preserve readable previews, optional source/diff, version-linked discussion, and stable layout under streamed updates. [P2, P3]

S1 uses these meanings with a simple pulse, activity view and required-action alert. S2 adds the full attention selector and milestone-capture presentation. The new prototype-source editor is not the same feature as automated exact edit enforcement; the plan separates them explicitly.
