## Outcome

Plan: [docs/plans/personal-answers.md](../plans/personal-answers.md), written before any code.

### A2-P01: automatic origin
- A turn is **automatic** exactly when a 0098 `personal_inputs` row exists for (owner, turn).
- Inside 0102's guard, under the held space:
  - An automatic turn needs its input's **latest** decision to be `admitted`, for this turn and the current epoch.
  - Otherwise it answers `not_admitted`, with a diagnostic. This covers no decision (a record-only input), `waiting`,
    `cancelled`, and another turn or epoch.
  - Only a turn with no input row reaches 0080 as legacy.
- Without 0102 (`personal-answer-effects.ts`):
  - The origin is read positively, in the reservation's own transaction.
  - An automatic turn reserves nothing (`not_installed`), unless its answer is already kept.
  - A failed read throws; nothing catches it into a fallback.

### A2-P02: kept answers first
- **Kept answers first.** The guard reproduces 0080's no-effect prefix verbatim, in 0080's order (`kept`, `lost`,
  `not_current`), under `personal_hold()`, before anything is compared. It does not call 0080 to discover the outcome.
- **The fresh branch.** Only the genuinely fresh branch compares profiles. On a match it delegates to
  `reserve_personal_answer`, unchanged: same ledger, binding and outcomes. The lock order stays space, then payer (the
  payer is taken only inside 0073).
- **The runner.** It still reads a kept answer before asking, so a kept answer is written with zero calls whatever the
  live profile is.

### A2-P03: refusal diagnostics
- **Identity:** `personal_answer_effect_refusals` keeps one row per (owner, input, decision seq, epoch). Seq 0 is the
  explicit no-decision identity.
- **Upsert:** a repeated wake or replay updates the same row. `attempts` is capped at 1000; `first_at`/`last_at` are
  kept.
- **Bounded contents:** finite reason and field-name enums only; values cannot be stored (a CHECK refuses any other
  field name).
- **Access:** owner-only RLS SELECT, no write grant, and cascades from the input, the turn and the decision (erasure).
- **Returned, not raised:** the guard returns its refusal, so the row commits with the transaction, and the API throws
  `CompanionRefused` only afterwards. No 0101 decision is appended and no profile is changed.

### A2-P04: profile comparison
- **Fresh profile per call.** `answerProfile(settings)` builds the exact closed A1 profile from the live settings
  again on every reservation. It returns null when 0101 would refuse that profile; the A1 validator is reused, not
  duplicated.
- **What the guard compares:** each field of the admitted decision's frozen profile (owner, payer, routeId,
  roleDigest, provider, model, reasoningEffort, maxTokens, the four prices, version), plus whether the payer and route
  arguments are the profile's own.
- **What it refuses:**
  - any difference: `profile_mismatch`;
  - a profile 0101 would not accept (for example an empty effort, which `liveSettings` allows): `profile_unsupported`.
- **Unaffected:** legacy turns and kept reads.

### A2-P05: the same runner resumes
`CompanionRunner.resume(owner)` reads `next_personal_reply` as the owner and calls the same `answer()`. That keeps
the same `serves`, claims, `inFlight`, `running` and `closing` behaviour, and the same order. There is no timer, loop,
claim reset or `asked_at` write. It never rejects; errors go to `onError`.
- **R1:** an `onReady` hook resumes the live companion's single enrolled owner once.
- **R2:** after commit, on the new Answer send and retry, and on the legacy send and retry. Replays wake too. Cancel and
  GET wake nothing.
- **Rehearsal:** a companion that is not live never answers an automatic turn (`AutomaticNotLive`). Its origin is read
  first, and a read error fails the turn.

### A2-P06: the HTTP surface (A53)
- **Routes:** `POST /api/v1/personal/answers`, `/{inputId}/retry`, `/{inputId}/cancel`, and
  `GET /{inputId}/decisions`.
  - Closed `personal_answer_v1` schemas; the actor is server-derived.
  - No profile, payer, route or model in any request.
  - The decision list carries identity, decision metadata and times in seq order, and omits the profile.
- **Switch:** `personalAnswers` is off by default (404), and `server.ts` does not set it.
  - On, `buildApp` refuses it without a live companion whose profile 0101 accepts.
  - `/ready` requires 0101's writers and 0102 only when it is on.
  - The guard and the drain are not gated by it.
- **A52:** `/personal/inputs` keeps the same receipt bytes in both states (proved by a cross-app replay).
- **Errors:** 0101 refusals with SQLSTATE 55000/54000 answer `invalid_state` (409) in our own words.

### Observed at `e864`, not changed beyond R2
The legacy wake `answer(turn)` for a turn that is not the oldest waiting stalls that turn: its own run holds it in
`inFlight` while the chain answers the older turn. R2's `resume` wakes the oldest turn directly, so the A2 code no
longer takes that path.

**The defect.** A53 declares `inputId` `format: uuid`. The route checked it with the shared lowercase-only

The idempotency semantic `{inputId, expectedSeq}` therefore names one input under every spelling. Left unchanged: the
shared `UUID_PATTERN`, A53, the generated files, SQL, persistence and every guard.

## Repair A2-F02: a waiting original stays pending while its answer cannot be made (child of `4a15`)

**Task.** `INC03-CC-003-A2-F02-READINESS-REPAIR-001` (`f1acfee9…`), from the independent
`INC03-CC-003-A2-F01-PR510-SOURCE-FINAL-001` (`1354631d…`). That review confirmed the automatic P1 comment 4556204505
(review 5881851671, thread `PRRT_kwDOUqJnR86200zk`) as A2-F02.
- Read alongside: the supplemental causal evidence (ZIP `d1e8b102…`, SUMS `03cff0f6…`) and the FIFO clarification
  (`301b0e51…`).
- One signed sole child of `4a1528263f`, on branch `inc03-cc-003-a2-f02`. Not published.
- Paths written: `apps/api/src/companion.ts`, the API DB test, the plan and this handoff. `app.ts` was not needed:
  R1, R2 and the chained queue all go through the runner.

**Cause.** 0101's writer, granted to `sophia_api`, can leave an admitted automatic turn pending before 0102 is installed
or while the payer is no longer admitted. The runner claimed it anyway; the reservation then refused it (`not_installed`
or `not_admitted`), and its generic failure path marked the turn `failed`, which pending-only selection never resumes.

**Repair.** `CompanionRunner` decides before any claim whether a live companion may take the turn now (`eligible`):
- **Legacy turns:** yes, as before.
- **Automatic turns:** only with 0102's guard installed and the companion ready (`Companion.ready`). Without those, only
  an answer already kept is written, with no call.
- **Otherwise the turn is deferred:**
  - nothing is claimed, failed, reserved, prepared or decided;
  - `asked_at` and the frozen admission are untouched;
  - the bounded drain stops (`run` does not chain), so the same head is never selected again, its own in-flight run is
    never awaited, and no timer or polling is added.
- **A failed read** is reported through `onError` and defers. It is never taken as legacy.
- **Unchanged:**
  - the rehearsal keeps its explicit refusal of automatic turns;
  - with the guard installed and the companion ready, the guard's refusals still fail the turn explicitly;
  - the two-minute lapse is the existing one;
  - turn order is FIFO (SQL `next_personal_reply`/`claim_personal_reply`, frozen). A deferred automatic head holds a
    later legacy turn behind it; both stay pending until a legitimate wake, after the prerequisites are back, answers
    the original and then the legacy turn, each once, if they are still within the existing window.

**Evidence, executed on the repair's bytes.**
- **The new A2-F02 suite (5 cases)** runs on a genuine 0001–0101 database: a directory of links to the real migrations;
  the admitted originals are made by 0101's own writer as the API role. Because 0070's role lets a cluster hold one
  migrated installation at a time, this last suite retires the file's main database first.
  - R1 with the switch off or on: pending, unclaimed, `asked_at` unchanged, 0 prepares, 0 usage, one decision, and
    `/ready` 503 when the switch is on.
  - R2:
    - a legacy turn before 0102 is answered once;
    - after it, an admitted original and a later legacy send stay pending and unclaimed, with no answer, no new
      prepare and one usage row;
    - a direct `resume` ends within 3 s.
  - Kept-first while 0102 is absent: written with 0 calls.
  - After installing the real 0102 file, R1 and an R2 wake answer each waiting original once, then the held legacy
    turn, with the original's decision count unchanged and no refusals.
  - With 0102 installed and the payer no longer admitted: the turn waits, `/ready` answers 503, and the next start once
    the payer is re-admitted answers it.
- **The full API DB file plus `personal`, `personal-inputs`, `readiness` and `personal-live`:**
  - On the pre-final test bytes: 99/99.
  - On the staged tree `64f5e3a7`: 100 tests, 99 pass. The 1 failure is the inherited, unchanged
