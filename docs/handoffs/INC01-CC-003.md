## Outcome

The path from Sophia's worker to an owner's own machine, as source with real database behaviour, proven only with
fake and disposable parts. The plan is [owner-host-transport.md](../plans/owner-host-transport.md).

1. **Pairing** (0093). An owner makes an expiring (≤ 600 s), one-use pairing for one of their own `linked`
   connections. The 256-bit code is returned once; only its SHA-256 is stored. Redemption consumes the pairing and
   binds a host atomically under a row lock. A replay with the same code and capability (a lost reply) answers the
   same host, marked `replayed`. Another capability, expiry, revocation, a revoked connection or a racing redemption
   is refused.
2. **Host capability.** Generated on the host (`scripts/owner-host.ts capability`); only its hash reaches Sophia. It
   authenticates the host channel and nothing else.
3. **Hello.** The host's identity (journal, environment, adapter pin, profile and revision, account, T3 namespace) is
   bound at its first hello and never changes. A different hello is a `conflict` listing the changed fields; nothing
   is delivered until a matching one.
4. **Exchanges.** The worker's `send`, `reconcile` and `observe` of a 0092 operation become durable, idempotent
   exchanges (the same key with another payload conflicts), bounded by a deadline (1–120 s) and 64 KiB.
5. **GO ledger.** A host may call its gateway only after a GO granted by the database, immediately before the effect.
   GO and delivery each recheck 0092's own `owner_runner_ineligible`, the operation's binding to the host's journal,
   owner and environment, the host's identity against the operation's frozen route, the hello and the host state.
   Fail closed: an unreachable or unconfigured GO is no GO.
6. **Port proxy** (`OwnerHostPortProxy`, a `SophiaRunnerPort`). Never granted GO → `refused` (nothing could be sent);
   granted GO and no answer by the deadline → `unknown` (reconciled by the original identity, never resent, never a new
   key); a receipt under any namespace but the host's bound one → `unknown`. Reconcile and observe are never
   `refused`.
7. **Loopback T3 MCP transport** (`T3McpTransport`, a `T3Transport`). Streamable HTTP 2025-06-18 as T3's own peer client
   speaks it at the pin; loopback only, no redirects, bounded time and bytes, `T3_TOOLS` only, for the bound
   environment only; the bearer is read per request from a file reader and never leaves the module; reasons are
   redacted. The namespace is declared and persistent, never derived from `Mcp-Session-Id`.
8. **Owner-host agent** (`OwnerHostAgent`). Hello, poll, GO, gateway, answer, sleep. Not a scheduler or continuation
   owner: Paperclip stays the continuation owner. It reopens the same journal after a restart.
9. **Fencing.** Retire, revoke or re-pair cancels create and input sends not yet granted GO; stops, reconciles and
   observes continue through a retired host. Revocation settles nothing: operations keep their state and reservation.

Everything stays off: no route mounts the host or owner functions, the worker is not wired, no qualification exists
in production, and the CLI's `redeem` and `run` refuse.

## Residual risks, stated plainly

- The GO ledger's `refused` rests on the database's durability: a restore to a point before a recorded grant would
  answer `refused` for a send that may have happened. The agent never answers anything but `refused` for a send it was
  never granted, and logs a ledger disagreement instead of claiming either way.
- A host is trusted to speak for its own journal: a gateway `refused` or `rejected` it reports is recorded as such
  (0092's existing rule).
- Two machines holding one capability with different journals make each other's hellos conflict, so neither is served
  until one stops; that is a deliberate refusal, not a merge.

- No push, PR, merge, deploy, account, grant, native, provider, voice, release, UI approval or AC promotion was made.
  The source-exposed privileged release hold remains operationally unqualified.
