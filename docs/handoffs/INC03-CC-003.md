## Outcome

The foundation is source-only and unreachable: nothing calls it from a request, and the package index does not export
it. The plan was written first (`docs/plans/personal-admission.md`): closed types, every decision state and reason,
operation and replay identity, the lock order, the five clauses and the limits.

**New records:**
- `sophia.personal_input_decisions`: append-only and content-free.
  - Keyed by owner, input and seq (1..100), with owner-composite FKs to the input and its turn, ON DELETE CASCADE.
  - Columns: epoch, operation, outcome, reason, policy/version/family/basis, an explicit `late`, the frozen trusted
    profile (send/retry) and `admitted_at` (admitted only).
- Owner-only RLS; SELECT to `sophia_api`; no write grant.
- Triggers refuse every update, and every delete except the erasure's foreign-key cascade.

**Three new writers,** EXECUTE `sophia_api` only, SECURITY DEFINER with a fixed search path:
- `send_personal_answer_input`
- `retry_personal_answer_input`
- `cancel_personal_answer_input`

They form the new versioned operation `personal_answer_v1`. The input itself is still an `automatic_v1` record in
0098's table. The old record-only writer, its route, body and flat receipt are untouched.

**Decision rules:**
- **Send** decides at once (seq 1):
  - **admitted** when the trusted profile's payer is admitted for the calling owner (a plain read, no payer lock, no
    reservation). The turn goes `recorded → pending`, and `asked_at` is set to the decision's `admitted_at`
    (`clock_timestamp()` after every lock).
  - Otherwise **waiting / payer_unavailable**: the turn stays held.
- **Retry and cancel** are separately keyed and name the seq they expect. Stale is `40001`. A decided, cancelled or
  record-only input is `55000`.

| Clause | How it holds (tests in `personal-admission.db.test.ts`) |
|---|---|
| V2-C01 replay | Every mutation's replay returns the receipt it remembered, with its own decision. | V2-C03 frozen profile | Stored with each send and retry decision for A2's comparison. Admission is eligibility only. The A2 effect guard is **not implemented** (below). |
| V2-C04 new operation | Request operations `send_answer_input`, `retry_answer_input` and `cancel_answer_input` share the owner's one key namespace. Every cross-operation reuse and every changed semantic is `23505` (seven cases, plus the old `automatic_v1` contract name refused by the new operation). Off-created inputs can never be retried into an answer. No HTTP here. |
| V2-C05 cancel | Only a waiting input; terminal. A lost cancel ACK is reconciled by its same-key replay before a correction is sent as a new input. A retry and a cancel at the same expected seq serialize (both orders, observed lock wait): one commits, the other is `40001`. Cancel after admission is refused (`55000`). **The admitted-but-not-paid correction is an AC-03-12 remainder.** |

### The A2 effect guard (required, not implemented here)

Before **any** fresh paid reservation or provider call for an automatically admitted turn, A2 must compare the decision's
stored `profile` with the live call's profile, field by field: owner, payer, route, role digest, provider, model, effort,
ceiling, prices and version.

**Covered paths:**
- the R1 startup drain;
- an R2 replay wake;
- queue chaining;
- the flag-off drain;
- a same-owner legacy `retry_personal_turn` of an automatic turn. Characterized here: an admitted turn left past two
  minutes reads failed, and the legacy retry re-asks it while adding no decision.

**Rules:**
- A mismatch fails closed with a truthful reason. There is no rebase or fallback.
- Kept settled answers (0078), authorized reads and cost reconciliation need no new paid call.
- Legacy turns without a decision stay legacy.

## Decisions and changes

- New request operation names and the `personal_answer_v1` contract were chosen to satisfy V2-C04. The input row keeps
  `interaction_contract = 'automatic_v1'`, because 0098's table CHECK requires it and that table is not edited.
- The profile excludes `credentialRef` and the provider profile, which name a credential. The model is bounded to 200
  characters and the effort to 64, with no control characters. This is stricter than the live parser, so a live model
  name with a control character would be refused (fail-closed).
- Cancel leaves the turn `recorded`: the owner's words stay held and out of every context (0099).
- Decision seq is capped at 100 per input (`54000` past it).

**Defect.** `personal_answer_profile` accepted any non-negative JSON number as a price. So a direct SQL send with
`prices.input = 1e400` committed a waiting decision whose profile JavaScript reads as `Infinity`. The owner's typed read
then failed. There was no public route, paid call or payer effect.

**Repair** (migration 0101, its SQL test, the DB test, this handoff and the plan; `personal-admission.ts`
byte-identical):
- The existing rule is kept: a JSON number, and every negative refused (`price < 0`).
- One exact bound is added: a price `>= 2^1024 - 2^970` (the first value JavaScript reads as `Infinity`) is `22023`.
- Nothing is rounded, clamped or rewritten, and no cap or price policy is introduced.
- **One representation difference, recorded and kept** (per the root's scope clarification): a negative decimal of
  magnitude at most `2^-1075`, e.g. `-1e-400`, reads `-0` in JavaScript, so the typed guard accepts it. SQL keeps
  refusing it, as it refuses every negative. Producers never emit it (`JSON.stringify(-0)` is `"0"`), and SQL is only
  ever stricter there.

**Evidence** (raw logs in the repair handback; disposable PostgreSQL on 127.0.0.1:55495):
