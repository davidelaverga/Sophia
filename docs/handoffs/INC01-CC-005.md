## Repair 5 (gate INC01-CC-005-repair4-SOURCE-FINAL-001: NATIVE4-F01, P2, repaired)

One signed sole child of the published `a528ab84`. Only the journal (`runner-journal.ts`), its lock
(`runner-journal-lock.ts`), their tests and the gateway test, the owner-runner operations plan and this handoff change.
No helper file was needed. No SQL, A47 or A50, record format, gateway, channel or transport changes, and the
source-map documents and the repair-1 to repair-4 closures are untouched.

### The defect

The 0700 and 0600 modes applied only on creation. An existing journal path was used as found when created, loaded,
torn-repaired and appended to: a readable 0644, 0640, 0660 or 0604 file, a symlink (to an empty file, a valid 0600
journal, or nothing), or a file in a directory others can write. Each step reopened it by name, following links. So
replacing the path after opening redirected the writes past the lock and length fence.

### The private path

- **The directory.** Before the lock or any file is created, the journal's real directory must be this uid's and
  writable by no one else. Every ancestor must be this uid's or root's, and not writable by others unless sticky.
  Nothing is chmodded or chowned.
- **The file.** It is opened once with `O_NOFOLLOW` (a missing one is created `O_CREAT|O_EXCL|O_NOFOLLOW`, 0600). It
  must be a regular file of this uid, with no group or other permission bits and one link. Otherwise it is closed and
  refused, with its bytes and mode unchanged and the lock released.
- **One descriptor.** Loading, torn-line repair, the header and every append go through that one descriptor. Each
  append also rechecks it, and checks that the path still names it (device and inode). A replaced or symlinked path
  fails closed before writing. The gateway journals the intent before any T3 call, so there is no native effect.
- **The lock.** Created and read with `O_NOFOLLOW`. A symlinked lock is unreadable, so it is refused, never recovered
  over.
- **Existing unsafe journals are refused, never adopted.** Their operations keep their identities, and the owner fixes
  the path; one made private again reconciles by its original identity.
- **Limits.**
  - POSIX hosts only: elsewhere the journal refuses to open.
  - This uid and root are trusted.
  - Ancestors are judged once, at opening.
  - The lock is per host.
  - No filesystem's isolation is qualified by this.

## Repair 6 (gate INC01-CC-005-repair5-SOURCE-PRE-PUSH-001: NATIVE5-F01, P2, repaired)

### The defect

Every lock read opened `<journal>.lock` read-only, without `O_NONBLOCK`, before checking it was a regular file:
acquisition with its stale re-read, `assertHeld` before each append, and `release`. A FIFO there made that synchronous

### The fix

That one reader now opens `O_RDONLY|O_NOFOLLOW|O_NONBLOCK`, and reads only a regular file.
- A FIFO, directory, symbolic link or other file reads as an unreadable lock, at once and without consuming anything.
- At acquisition it is refused (`JournalLocked`, never presumed stale).
- At `assertHeld` it is "no longer ours", so the append is refused before any T3 call.
- At `release` it is left in place, never unlinked or adopted, and `close()` ends.
- Recovery's stale re-read goes through the same reader. That shares the fix by construction; no recovery race was
  forced or is claimed.

**Corrected wording (repair 5's plan limits).** Network filesystems are not detected (there is no filesystem-type
check). They are unsupported and unqualified, not refused.

- a queued run later cancelled by an interrupt;
- an unrecognized status.

A new gateway replayed the false `started` from the fsynced journal without reading.

### The fix

An input reconciled from a read is `received` only on positive evidence about the exact run its exact message names:
- **queued:** the run is listed `queued`;
- **started:** the run is listed in T3's active-and-not-queued set (`preparing`, `starting`, `running`, `waiting`), or
  it is the read's `activeRunId`. T3 derives that over every run, so it is the same run id, never a rebinding.
- **unknown, with nothing final journaled:** the run is absent and not active, terminal (a `cancelled` or `completed`
  status alone proves no start), unrecognized, or listed `queued` yet named active.

The possible send stays journaled, so it is never sent again, and a later positive read resolves it with no new native
effect.

**Unchanged:**
- create reconcile, send-time receipts, Stop settlement, receipt and malformed-run checks;
- fixed diagnostics and privacy;
- window and page bounds, and no new call or loop.

**The consequence:** a lost input whose run has already ended when it is reconciled stays `unknown`, and an operator
settles it. In the worker crossing, the Stop that cancelled such an input's queued run stays `received`, its binding
`stopping` and its reservation held.

## Repair 10 (gate INC01-CC-005-repair9-SOURCE-FINAL-001: NATIVE9-F01 and F02, P1, repaired in source)

One signed sole child of the published `55839827`. It changes the same six paths as repair 9: `t3-port-mapping.ts` and
its test, the gateway test, the worker DB test, the plan and this handoff. The gateway, the worker, SQL, contracts, the

### The defects

- **F01.** `messagesIn` let the last row for a message win. A page naming the original input's message with no run and
  then a run, or with another run and then a run, reconciled a possibly-sent input as `received started`. That answer
  was fsynced and replayed after a reopen, and it cleared the SQL input barrier. The Stop and binding then settled with
  0 reservations, while the same input was still in transit.
- **F02.** A complete-looking summary could name an active run that is not in its run list, with `runCount` 0 or with
  another run listed. An item naming that run got `started` from the gateway's active fallback. A list longer than
  `runCount` was accepted too. The same false receipt, barrier, Stop and binding followed, but 1 reservation stayed held
  for the unresolved input.

### The fix

The mapping only; the gateway is unchanged.
- **One association per message.** Rows naming the same non-null message id must name the same run, or all no run.
  - Identical repetitions and rows with no message stay coherent; the pin does not make message ids unique.
  - A conflict makes the whole page no evidence, in either order. Neither the first nor the last row is chosen.
- **A summary consistent with its own runs.** These make the whole page no evidence:
  - more listed runs than `runCount`;
  - a complete list (as many runs as `runCount`) without its non-null active run.

  A truncated window may still omit the active run, so the repair-8 fallback stays for it.
- **Unchanged:** ids stay exact, and repair 8's and repair 9's closures hold.
- **Limit, stated plainly:** the decoder judges one page. A row for the same message on a page the gateway never reads
  is not compared.
