## INC01-30813-EXPIRY-F01 (P1, inherited; ACKed and closed here in 0096)

**Cause.** 0092 judged connection and qualification expiry at transaction start. A prepare-send that waited on the
project lock past the expiry still marked the possible send, and the dispatcher sent it.

- every expiry uses `clock_timestamp()`;
- prepare-send runs the whole recheck again after the account reservation's lock, immediately before the possible send;
- admission rechecks expiry after its last lock wait, before any write;

**Regressions.** Real PostgreSQL, through the dispatcher, gateway, fsynced journal and FakeT3, each with an unexpired
control:
- prepare-send waiting on the project, for a qualification and for a connection;
- an input waiting on the account reservation;
- an admission waiting on the goal.

## Repair 2 (gate INC01-CC-005-repair1-33c020af-SOURCE-FINAL-001: NEEDS_REVISION, two P1 concurrency classes, both repaired)

### The authority lock

**The projects row is the shared authority lock:**
- `revoke_owner_runner` is replaced with the same signature, error and privileges (migration owner only) and fixed
  `search_path`. It locks the project first, then the qualification.
- `declare_owner_runner_source_policy` does the same.
- Prepare-send, which already holds the project, now also holds the operation's resource, connection and qualification
  rows `FOR SHARE` (`owner_runner_lock_authority`) until it commits.
- `owner_host_go` first identifies the exchange's project, without a lock: that lookup authorizes nothing, and
  unknown-capability and foreign-exchange answers are unchanged. It then takes the project `FOR SHARE`, authenticates
  and locks the host, locks and revalidates the exchange, and takes the authority rows `FOR SHARE`. The final recheck
  (including the cumulative input lineage), the payload read and the grant all happen under those locks.

**Lock order:** project → host → exchange → resource, connection, qualification. No writer takes these in another
order. Erasure, membership changes and admission already hold the project first.

### Outcomes

**The first to commit wins:**
- A revocation, erasure or direct connection revocation that commits first makes prepare-send deny, or GO refuse with
  no payload and no native call.
- A decision that holds the lock first commits first, and the later change waits. The possible send or grant stays,
  with its original identities, binding, account reservation and unknown reconciliation. Nothing is falsely unsent,
  purged, refunded, reset or resent.

## Repair 3 (addendum INC01-CC-005-33-73-PAIRING-AND-COVERAGE-ADDENDUM-001: PR505-33-73-F03, P1, repaired)

### The defect

Two distinct codes for one connection, redeemed at once:
- each locked only its own pairing row;
- they shared the connection `FOR SHARE`;
- each retired only the hosts it saw committed.

So both inserted, and two hosts stayed live.

### One live host per connection

- **Serialization.** `owner_host_redeem` is replaced: the same signature, answers, `SECURITY DEFINER`, pinned
  `search_path` and privileges (`sophia_api` only, unwidened). It serializes per connection with a transaction advisory
  lock that no other path takes.
- **Lock order.** Pairing `FOR UPDATE` → the connection's redemption lock → its live hosts `FOR UPDATE` → the connection

  qualification) and in retirement and revocation (host → exchange).
- **The decision after every wait, before any change.** The code's expiry and the connection's owner, state and expiry

- **The invariant as a constraint.** A partial unique index, `owner_hosts_one_live_per_connection`. A database that
  already holds two live hosts for one connection stops the migration with a named error. The migration retires
  nothing: which host keeps serving is the owner's decision.
- **Unchanged.** Same-code and same-capability replay, the used-code conflict, TTL, owner-only pairing and capability
  authentication.
- **A replaced host is retired, never revoked.** It keeps reading, reconciling its unknown create by its original
  identity, and carrying its qualified Stop. Nothing is unsent, refunded, settled or unbound.

## Repair 4 (gate INC01-CC-005-repair3-map-compose-SOURCE-PRE-PUSH-001: CC005-R3-F01, P1, repaired)

The development child is a child of the composed `50cd1054`. The publication candidate is one signed child of the
published `33c020af` with the same tree, so the three source-map documents stay those of `84e01bc9`, byte for byte. The
repair is in `0096` only. The three closed concurrency classes (revocation, source erasure, pairing redemption) keep
their locks and order.

### The defect

Locks serialize writers but cannot hold time still. Prepare-send's last recheck, and GO's deadline, recheck and payload
read, came before writes that can wait on a lock:
- prepare-send: the operation and command `UPDATE`s and the event `INSERT`;
- GO: the exchange `UPDATE`.

A qualification, a connection or an exchange deadline could run out during that wait. The send or grant, with its
payload, then still happened.

### The decision after the last write

- **Prepare-send.** The possible-send writes run in a PL/pgSQL block (a subtransaction). Its last statement is the whole
  send check again at `clock_timestamp()`, with the payload re-read. On a refusal the block is rolled back: no possible
  send, no command change and no `sending` event to replay. The operation is then denied through
  `owner_runner_deny_prepared` like any earlier denial. This holds for every kind, a Stop with its usual check.
- **GO.** The grant's `UPDATE` runs in a block whose last statement is the final check: the exchange deadline, the
  whole `owner_host_send_refusal` (both expiries included) and, for v2, the private body re-read. On a refusal the block
  is rolled back: no grant, no `go_count` and no payload. The answer is the existing refusal: a first GO denies the
  exchange, and a GO after an earlier grant only records it. A lapsed deadline answers as before.
- **Locks.** The final checks take no new lock: every row they read is held already. The order project → host →
  exchange → authority rows, and the per-connection pairing rule, are unchanged.
- **Earlier effects.** An effect already possible is untouched: it keeps its binding, reservation, journal,
  reconciliation and qualified Stop. Nothing is unsent, refunded or reset.

### Proof

The barrier is a real table `SHARE` lock that blocks only the final write. Each case asserts that the waiting backend,
named in `pg_locks` and `pg_stat_activity`, was waiting before the limit and still waiting after it. Every wait is
bounded.

The tests run through the actual dispatcher, persistence, `OwnerHostPortProxy`, `DbHostChannel`, `OwnerHostAgent`,
gateway, fsynced journal and FakeT3:
- prepare-send waiting on its event `INSERT` (qualification and connection) and on its command `UPDATE`
  (qualification), each with a valid control;
- GO waiting on its exchange `UPDATE` (qualification, connection, exchange deadline), with a valid control;
- an earlier received create kept when its input is denied late, at prepare and at GO. The GO case also takes its
  qualified Stop through the same host.
