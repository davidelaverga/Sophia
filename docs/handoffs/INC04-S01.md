## Outcome

`@sophia/domain` now has `evaluateSelection`, a pure, deterministic, advisory function that, given one trusted snapshot of a new-work request and its candidate resources, returns either a proposed candidate with ranked alternatives or a specific waiting, denied, blocked, refused or invalid result, with closed reason codes for every candidate. `projectSelection` is the only serializable view of a decision, filtered for one viewer.

What it does not do: it reads nothing, admits, reserves, dispatches, rebinds, resumes or calls nothing, has no runtime caller, no persistence, schema, migration, contract, route, flag or UI, and changes no existing behaviour. Nothing in its input authenticates anything: a future trusted server caller must derive every fact and existing admission must recheck all of them before any effect. It is one source component, not a live S01 service, not INC04 and not activation.

No acceptance case has evidence from this work. All eighteen AC-04 cases remain open, as do every native, owner, deployed-authorization and application gate.

## The contract implemented

The R2 proposal with all seven corrigenda of the independent review and root choices C01 to C07:

- **Order.** Structural validation (`invalid_input`), then active work (`refused_active_work`), then request-wide holds (`blocked`: goal hold, stop or completion, mission Stop, source withdrawal, design hold, authority, an operation-level refusal, unproven independence, an unsettled prior attempt, each including unknown), then per-candidate filters, then the winning policy scope, then ranking.
- **Completeness (C01).** Limiting windows and protected-reserve dimensions are proved by a witness independent of the lists checked: a covered witness must name a non-empty required set and every member must be present and fresh; `none_applicable` must be explicit; partial, unknown or empty coverage fails closed. Reserve protection applies to every consuming role. A conservative no-reading policy replaces readings, never reserve protection.
- **Proofs (C02).** Conservative capacity policies, route overrides, cross-payer authorizations and project allowances are resolved propositions, checked for proposition, issuer, authorizer, exact owner/project/account-group/payer/route/family/operation scope, role, status and validity at `evaluatedAt` (a standing policy may have no expiry). Unknown, stale, revoked or mismatched proofs fail closed.
- **Authority (C03).** Cross-member use is derived from the owner and actor refs; contradicting facts are a `fact_conflict`. A required contribution grant that is null is `grant_missing`; the grant must cover the actual owner, project, role, operation and strict settings, with expiry judged at `evaluatedAt`. 0094's refusal codes pass through verbatim.
- **Modes (C04).** Pin selects only its target or waits/denies. Prefer with an absent target waits; a prohibited target denies; an unavailable target falls back within its payer, or to a payer named by a current cross-payer authorization, which never competes with an eligible target. An empty pool waits with `no_candidates`.
- **Settings (C05).** One effective strict setting (a manual request, else a winning Pin's; a conflict between them is invalid). Prefer and default seeds are soft, proposed only when declared and granted for the candidate's own provider instance. Provider-native values are never equated across instances; accepted and observed settings are always `unknown`. Keyed facts (options, models, share grants) canonicalize identical duplicates and fail closed on typed conflicts (`true` is not `'true'`).
- **Projection (C06).** One whitelist for rows, proposal, alternatives, settings and fallback. A viewer the caller has not permitted to see the request gets one uniform restricted shape. Otherwise the resource owner sees its codes; a shared viewer sees only a coarse limitation and the fields shared with them; anything else is omitted, a hidden proposal is `withheld`, and no counts are given. The internal decision's throwing `toJSON` is an accidental-serialization guard only.
- **Determinism (C07).** The same canonical input gives the same data decision, including under any permutation of candidates, sets and keyed facts. Timestamps are strict RFC 3339 normalized to UTC microseconds. Errors and reported codes are sorted before bounded reporting, which never changes a status or a selection. The correlation tuple names declared input revisions and the normalized instant; it is not a proof of equal facts, an equal decision or a permission, and nothing is hashed.
- **Bounds.** Structural only, from existing conventions: 200 candidates (A51 page), 50 refs per set (0094), 20 per declared list, 10 options per model and 20 values per option (0096), 40 reported errors or codes (0038), 200-character refs and values. No quota, reserve, funding or provider number is introduced.

## Repair 1 (R1): payer privacy and caller input ownership

**INC04-S01A-69FC-F01, fallback payer relationship.** `fallbackView` emitted `crossPayer` when the proposal's payer was visible and the preferred target was merely visible. A target shared without `payer_scope` therefore revealed whether its private payer equalled the visible one: two views identical in every shared field differed only in `crossPayer`. Now the relationship is emitted only when BOTH payers passed the viewer's whitelist (the viewer owns the resource, or holds a current `payer_scope` share), and is otherwise withheld, uniformly (`null`). The internal decision's fallback, eligibility, cross-payer proofs, pool and ranking are unchanged; hidden resources and the restricted summary behave as before; with both payers shared or owned, the comparison is still shown.

**INC04-S01A-69FC-F02, caller-owned settings.** `canonicalSettings` copied the settings envelope and array but kept the caller's option objects, which `seal` then froze: a caller's mutable strict request became frozen, was the same object as the decision's, and a later edit threw. Now every settings object in a decision is new, so no object reachable from the input is reachable from the decision or its view; the caller's objects keep their values, descriptors, frozenness and extensibility, and a later edit by the caller changes neither the earlier decision nor its projection. Decisions stay deeply frozen, and already-frozen inputs are still accepted.

**Regressions.** Six reached assertions were written first and fail against the exact attempt-1 module, then pass with the repair: the same/different private target payer giving identical views, a target shared with no fields keeping its payer relationship private, and the caller-ownership check for a manual strict request, a winning Pin, a Prefer soft seed and a candidate default seed (whole-input object reachability, frozenness of every decision object, descriptor and state preservation, and stability after a caller edit). Controls for a hidden target, a restricted summary, a proposal whose payer is not shared, neither payer shared, and both shared or owned pass before and after. Fixtures remain synthetic-not-AC-evidence.

## Repair 2 (R2): a native candidate needs a current host

**PR #515 finding 4561188316 (P2), on `f3cf09af`.** `qualificationFailures` failed a candidate whose host was offline, stale or unknown, but never checked whether `not_applicable` fit the route. An otherwise eligible native candidate reporting `qualification.host: 'not_applicable'` therefore had no failure, entered the eligible pool and could be ranked and proposed without any current host, contrary to INC-04 R01's current host and auth health hard filter. The same independent reviewer confirmed it; `f3cf09af` and its earlier CORE and PRE remain immutable history.

**Repair.** A native candidate whose host is `not_applicable` now gets `fact_conflict` (proof missing): a native route runs on its owner's host, so the fact contradicts the route. Because filters run before mode application and ranking, this holds for own-use and properly qualified cross-member candidates alike, and in Auto, Prefer and Pin: a pinned target waits, a preferred target falls back under the existing same-payer or authorized rules, and such a candidate is never ranked or proposed. An API candidate with `not_applicable` stays eligible; native and API `offline` and `stale` keep their availability codes, `unknown` keeps `host_unknown`. The R1 payer-privacy and input-ownership fixes and the seven contract choices are unchanged.

**Regressions.** Five tests were written first and fail against the exact `f3cf09af` module with assertion errors, then pass with the repair: every typed host on both routes (the table also holds the existing controls), a qualified cross-member native candidate, Pin, Prefer and ranking. ## Repair 4 (R4): strict settings are shown only to the viewers of their exact origin

**PR #516 finding 4562079386 (P2), on `865401b7`, and its same-cause row sink.** `projectSelection` checked only the coarse summary permission and then returned the effective strict settings unconditionally. A viewer allowed to see the request's summary therefore saw the exact provider instance, model and options of the manual request or winning Pin, even when the resource was hidden from them, shared without settings, absent or contradictory. The same independent reviewer confirmed it, and found a second sink of the same cause: while strict settings are in force every row's soft seed is the strict value, so an unrelated resource the viewer owns, or one shared with them with settings, carried the private strict value as its seed, and a visible proposal copied it. `865401b7` and its earlier CORE and PRE remain immutable history.

**Repair.** The input takes one optional trusted-caller fact, `strictSettingsDisclosure`: an origin (the manual request, or the exact winning Pin by level, target and revision) and the viewers allowed to read it. The decision keeps the resolved viewers internally, only when the origin matches the effective strict source exactly by the existing precedence. Otherwise nobody is permitted. Nothing is inferred from the summary, from owning or seeing a resource, from equal values or from the proposal, and a missing field discloses nothing. The projection shows the top-level strict settings only to those viewers, and every strict-derived seed, in candidate rows and in the proposal, needs the same permission on top of the row's existing owner or settings-share rule. Otherwise the seed is omitted, never replaced by another value. Without strict settings, soft Prefer and default seeds keep their existing rules. A malformed descriptor is invalid input under the existing bounds; a well-typed but mismatched origin only discloses nothing. Selection, strict evaluation, ranking, fallback, the uniform restricted summary, payer privacy, the native host rule and caller ownership are unchanged, and the descriptor is copied, never held or frozen. The kernel authenticates nothing: a future trusted caller must derive the viewers from a genuine current read permission on that request or policy record.

**Regressions.** New tests cover the reviewed matrix:
- manual and Pin origins with hidden, route-only, absent and contradictory resources;
- unrelated owned and settings-shared rows with matching and different settings;
- exact-origin owner and shared-viewer positives;
- manual and scope precedence, with wrong source, level, target or revision;
- no summary, and no strict settings;
- detachment and determinism;
- malformed descriptors;
- the guarantee that valid disclosure variations change nothing selected.

Against the exact `865401b7` module, the leak cases fail with assertion errors on both the top-level value and an unrelated row's seed, and the existing tests pass. Fixtures remain synthetic-not-AC-evidence.

**Scope.** Only `allocation-selection.ts`, its test file and this handoff change; every other path stays as in `865401b7`. This commit's identity, checks and ordinary run are recorded in the external evidence packets, not here.

## Repair 5 (R5): a manual disclosure is bound to its request revision and current read

**PR #517 finding 4562616410 (P2), on `6ebf45e3`.** A manual strict-settings origin was only a kind tag. A descriptor derived for an earlier manual request, an earlier settings value or an earlier read audience therefore matched any later manual request, and its viewers saw the new provider, model and options at the top level, in every visible strict-derived row seed and in the proposal. The same independent reviewer confirmed it. `6ebf45e3` and its earlier CORE and PRE remain immutable history.

**Repair.** The input takes one more optional trusted fact, `manualStrictReadSnapshotRef`: the current read of the manual request, which the trusted resolver scopes to the actual request record (identity and version) and its current settings and read-audience generation. The resolver renews it whenever the request, its settings or who may read them change, even under an unchanged `requestRevision`, and derives the disclosure's viewers from the same read. A manual origin now names both the `requestRevision` and that read. A manual disclosure counts only when both equal the current input's.
- Without a current read, nobody may read the manual strict settings, though selection still uses them.
- A malformed read ref, or a manual descriptor without a valid `requestRevision` and `readSnapshotRef` (including an older kind-only descriptor), is invalid input, never a wildcard.
- The Pin origin, manual-over-Pin precedence, every sink and row whitelist from R4, selection, ranking, soft seeds, detachment and determinism are unchanged.
- Neither ref reaches the view or the errors.

**Limits.**
- The ref checks provenance consistency only. It proves no right, and no equality check can reveal a revocation if a caller presents a whole old input as current: current permission, rechecked before any effect, stays the trusted resolver's.
- `requestRevision` remains a correlation ref.
- No caller, cache or store exists yet, and none was added.
- No deployed exploit was established.
- Strict-null inputs without a disclosure need no new field.

**Regressions.**
