# Computer-use and contributed-resource qualification

## Supported environment categories

| Category | Evidence boundary | Initial use |
|---|---|---|
| Hosted Bot browser/computer | Provider documentation describes persistent browser, files and terminal; reliability unmeasured here | Selected account collection and read-only review of an exact internet-accessible preview |
| Native local commands/files | Separately approved local-execution path; device must be reachable | Inventory and collection from explicitly selected folders; originals unchanged |
| Desktop-proxied network | Depends on actual desktop/network route; do not assume all terminal traffic follows it | Internal preview only after exact route and disconnect behavior are tested |
| Local visual GUI via Cua Driver | Third-party installation/OS permissions, separate local-command policy | Optional later compatibility task, not first-release dependency |

Documentation sources: GB-WORK, GB-COMPUTER, GB-CUA. Their claims are capability inputs, not a benchmark or acceptance result. Native provider approvals, login, MFA and CAPTCHA remain owner actions. Do not automate credential capture, bypass a site's controls, strip frame/security headers, or infer a general right to scrape private assistant histories.

## Work selection

Prefer structured permitted connectors and file exports when available; visual interaction is for gaps where it adds value. A source inaccessible through a supported route is listed as inaccessible. Account-wide history crawls and broad device scans are not the default. For local input, disclose copying selected material to a cloud provider as a separate data movement; it is not implied by a later team-share permission.

After collection, a cloud analysis phase can continue on explicitly approved copied input while the laptop is offline. Work still needing an unsynced local file must show waiting_for_device. Closing Sophia alone should not stop admitted server-side work, either native or Bot. Multi-hour tasks need useful checkpoints and recovery evidence; duration alone does not justify a new provider.

## Browser-review assignment

Bind preview/deployment URL, exact source candidate/commit, allowed network targets, test-account role, viewport/journeys and forbidden effects. Use a staging/preview account with no production authority. Return steps, expected/actual behavior, repeatability, timestamp, screenshots/logs and limits. Screenshots may contain personal/client data and follow the same private-first rule unless a specifically project-scoped review was authorized.

Native visual review does not replace executable assertions. Compare against Playwright or the relevant existing application checks. A provider screenshot alone is not source identity; the preview service should expose a non-secret candidate marker where possible, and the Bot must report if it cannot verify it. Do not synthesize evidence for inaccessible journeys.

Test fresh and resumed sessions, changed screen state, stale authentication, device disconnection, a removed source and a late result. Separate necessary human steps (login/approval) from avoidable assistance. Record quality, intervention burden, completion, useful partial output and observed usage; no invented success percentage.

## Resource accounting

The connection contributes one owner account's available Bot allowance. Several Bots or routines on it are not separate balances. Current billing documentation describes eligible paid Cursor/linked individual Grok access and non-stacking grants; with on-demand disabled included allowance exhaustion stops work, while enabled overage limits are not hard mid-run cutoffs. [GB-BILLING]

For the pilot require the owner to confirm included-usage mode and identify any connected billable tools. Record whether the setting was owner-attested, observed in UI or provider-attested, with date. Do not claim Sophia continuously enforces a provider setting or knows remaining capacity without a verified API. Team-plan defaults can differ; verify rather than assume. No auto-purchase, link movement, added API key, paid fallback, another owner's account or unapproved external service charge.

Provider-managed model selection is not dsh-like control. Missing reasoning/model controls remain unsupported; choose task/output boundaries rather than inventing settings. Sophia hosting, storage, message processing and any personal Companion inference remain separate costs.

## Connection readiness

`connected` proves authentication only. `qualified_private_import`, `qualified_web_review`, `qualified_local_collection`, `qualified_wake_resume` and `qualified_project_peers` are independent evidence flags bound to actual provider/client/version/configuration. Configuration changes or material provider regressions invalidate the relevant flags. No green universal-ready label from a successful MCP tools/list.
