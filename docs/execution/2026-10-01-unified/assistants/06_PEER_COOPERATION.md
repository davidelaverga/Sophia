# Later cross-owner peer cooperation

## Preserve the one-template idea

Two owners can connect copies of the same Project Assistant and receive different roles per admitted assignment: competitor evidence, customer evidence, design alternative or independent review. The current mandate is task data; it does not mutate the permanent template or increase resource permissions.

Native Bot messaging/group features are evidence of provider-local cooperation, not proof of arbitrary personal cross-account control. Sophia's scoped software relay provides the cross-owner path. Tools transport messages and evidence; Sophia's reasoning concentrates on scope, significant disagreements and synthesis. [GB-WORK]

## Enroll the team edge explicitly

Only PA-04 introduces project peer recipient edges. Both owners must contribute their connections, allowed tasks, data scopes and spending policy. Project policy must permit disclosure to those external account environments. An owner cannot bind another person's assistant or cause their account to spend merely by mentioning its name.

Use an operational work assignment in Paperclip if that project has selected Paperclip. Store a single work mapping and route adapter; do not let the private inbox controller and Paperclip both continue the same assignment. A personal collection stays personal even when its owner participates in a shared project. Shared messages may refer only to project-published source versions or separately approved outbound snapshots.

## Interaction pattern

First collect independent findings when diverse evidence is useful. Then permit a small number of purposeful questions/challenges. Finally return revised contributions with sources, what changed, uncertainty and the exact candidate. Sophia compares contributions with the mission and presents a proposal; it does not automatically accept consensus or count two similar model answers as independent empirical confirmation.

Peer envelopes retain actual connection sender, source/assignment revision, recipient binding, reply and causal chain, bounded content and permitted evidence references. Validate every reference for the receiving owner/project before delivery. A peer cannot elevate a job from review to deploy, alter another owner's reserve, access their personal memory or issue direct admin requests.

## Wake and recovery

Use durable inboxes and substantive reply wakes, never synchronous model polling. Coalesce notifications; receipt acknowledgements do not wake the sender. Detect reciprocal waits and return a best-effort partial answer or a bounded lead decision instead of indefinite deadlock. Limit chain depth and exchanges in the accepted policy. Reconcile unknown remote activity before retry/reassign; a transport receipt does not prove incorporated guidance.

PA-04 acceptance includes two real owners, their correct payer attribution, one question whose answer changes the work, restart with pending mail, a removed member and a late reply. A market-research demonstration is appropriate here, not as a substitute for PA-01/02's privacy proof or the native three-engineer release.
