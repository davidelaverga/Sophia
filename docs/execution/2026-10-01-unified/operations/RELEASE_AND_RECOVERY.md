# Release, rollback and maintenance

## 1. Gates are scoped, not one giant global switch

Introduce typed coordination configuration with independent capabilities: operational projection, commission, dsh execution, owner-session execution, peer delivery, qualified permission response, advisory allocation, automatic handover, standing continuation and learning proposal. All new effectful paths start disabled. These are proposed gates to implement, not existing environment-variable names.

The pilot can expose a readonly projection without starting work, and can use one managed dsh task before enrolling external engineers. A missing PDF host does not block the first management proof. A missing stop/authority guarantee does block the affected live route.

## 2. Exact deployment tuple

Record Sophia commit and schema/amendment versions; Studio/API/media/worker/runtime artifacts; dsh unit/preset digests; Paperclip server source/image/database migration version; plugin/adapter artifacts; Omnigent source/image and owner-native versions; secret-reference/configuration versions; enabled pilot projects and limits.

The source candidates in this pack are not deployment digests. Artifact metadata contains no secret or native provider login. Confirm licenses and preserve required notices for the exact donor artifacts before distribution; no license compatibility determination is claimed by this pack.

## 3. Reader-first rollout

1. Close the existing PR29 entry dependency through its actual approved process. Preserve 0018–0020 history and compatible text/voice readers; do not old-code-only rollback over new data.
2. Reserve and author fresh schema/amendment IDs in the actual checkout; record hashes and prove upgrade plus compatible read behavior on disposable copies.
3. Deploy readonly mappings/projectors and current-state readers first. Old and new work remain distinguishable by controller kind/generation.
4. Bring up private pinned Paperclip service/database and the plugin/adapter. Verify endpoint/network/auth isolation, restart behavior and effect permits while admission is off.
5. Enable one pilot project and one bounded new work item. Observe core issue/run, native attempt, candidate and stop/recovery evidence.
6. Enable each owner resource only after its enrollment/native tests. Enable peers only after cancellation, delivery dedupe and idle-wake tests.
7. Add planning, warning/handover, review and standing continuation per milestone evidence. Leave unqualified in-app permission and learned recipe features off.

One operator owns the exact release batch. Do not redeploy unchanged services purely for visual symmetry; retain and document compatible source/artifact identities. Do not claim that all services run the same SHA if they actually do not.

## 4. Recovery semantics

**Service outage:** retain last observed work status with freshness, prohibit unconfirmed new starts, and keep existing conversation/direct Stop working. An observer outage does not imply the owner process stopped.

**Feature rollback:** disable new admissions/automatic transitions while keeping compatible readers and control/reconciliation consumers. Drain/fence existing work and retain histories, candidates and grants. Do not drop tables or erase pending operations.

**Controller rollback:** no instant switch of active work from Paperclip to the old scheduler. Settle the old episode/effects; transfer under a new controller generation only after exclusive writer evidence. New work may use an explicitly selected qualified controller; failure alone is not permission for a silent fallback.

**Runtime rollback:** use the recorded earlier unit/artifacts and its supported log compatibility. Do not relabel the new lockfile as the old runtime. Failed/unpaired history remains explicitly unrecoverable unless a reviewed recovery exists; do not synthesize a successful tool result.

**Account revoke:** deny new uses immediately, attempt native stop/revoke under the actual grant, retain unknown settlement and invalidate associated capabilities. Do not replace the account with another owner automatically.

## 5. Minimal operational monitoring

Use deterministic checks for missing/uncertain bindings, stranded required action, stale telemetry, outbox lag and source-eligibility mismatch. Alert on meaningful changed conditions with dedupe. Do not schedule a generative progress report for every service heartbeat.

Operational diagnostics contain opaque work/source IDs, bounded result codes and timing. Personal memory, full native transcripts, credentials and default audio are excluded. Retention/deletion obligations cover both stores and owner-side artifacts; deletion completion needs actual supported receipts.

## 6. Upstream maintenance

Keep each donor pin and a short local patch list. Upgrade one donor at a time through contract/restore/control/permission/usage tests. Public method/package availability is not promise of stable semantics. Avoid a floating `latest` or automatic upstream pull in production.

The first maintenance exercise changes one harmless supported dependency in a disposable environment and verifies that an incompatible adapter/schema fails readiness rather than guessing. A broad upstream rewrite is not part of the founder pilot.
