# Studio, voice and the candidate under review

## 1. Preserve the current product center

Conversation and the living brief remain the primary experience. Add management as a supporting Work view and a compact attention region, not a replacement screen full of agent avatars. Manual edits, current scroll/focus and each participant's local view remain stable during incoming state updates. The saved-update indicator is driven by a durable receipt. [S02]

The minimum surface shows the current outcome, next meaningful checkpoint, actual candidate, pending guidance, required owner actions and **Review work progress**. Advanced details expand to resource/window state, exact versions, delivery receipts and execution evidence. Raw model reasoning, native tokens and private metadata never appear in ordinary UI.

## 2. Required views and actions

| Surface | Required behavior |
|---|---|
| Living brief | Retain existing side/full/mobile behavior; link accepted work/result decisions without duplicating the brief |
| Work card | Goal and current verified phase, owner/resource, next checkpoint, latest candidate and recoverable state |
| Resources | Separate contributed accounts; known windows/reset/age; connected versus ready versus executing |
| Required action | Correct owner/session/action, native-open path initially; only qualified in-app answers |
| Guidance | Recorded → queued → delivered/native-observed → verified-result when available; no false “applied” |
| Capacity warning | Exact pending steer with Confirm steer / Let project lead reassign and cancel |
| Review | Exact preview/source version, change/preserve targets, independent checks and acceptance choice |
| Return summary | What changed, what remains, whose decision is next and which source/result supports it |

No progress percentages invented from timers. Reconnecting describes the client, not a restarted task. A completed native run does not mean product accepted; a review with negative findings can itself be completed.

## 3. Text and voice integration

Add real work operations through shared authorized API use cases and matching tool declarations. Suggested semantic operations are `commission_work`, `review_work_progress`, `send_work_guidance`, `read_required_actions` and `decide_work_request`. These are proposed new tools; SCM-04/06 binds exact schemas and return shapes. A separate generic “execute anything” tool is prohibited.

Finish admission calls promptly with the real work/command identity. A background result arrives through canonical events and the current mission/work reader; do not send a second final result to a closed provider tool-call ID. Reuse the current single result-notice arbiter and interruption rules. Worker/tool/event/UI paths cannot each generate their own spoken success.

Preserve the current typed-turn recipient, connection generation, utterance and deadline through asynchronous tool continuation. A typed result must not leak into shared room audio. Lost/abandoned provider turns are fenced, not silently resubmitted. No new durable raw transcript retention is required for management. [S02/S05/S07]

Stop Speaking, Stop Looking and End exchange are distinct from Hold work, Stop work and disconnect resource. Ending voice must not revoke a valid standing work mandate or reopen itself when the work finishes. Member departure or eligibility changes can invalidate a context independently of voice controls.

## 4. Prototype and implementation continuity

Management can first coordinate a real small feature in an existing source tree. It does not need to wait for the entire image-generation and prototype platform. For the full creative episode, S1-06/S1-07 must separately provide actual editable prototype source, selected assets/tokens, interaction states and declared simulations.

The lead consumes that source bundle—not only a screenshot—and produces a work plan identifying missing services and preserved design constraints. Use SMC-M03's canonical source/artifact identity and storage/publisher once available. Avoid a second “Paperclip artifact store” that becomes the real user output by accident. A management-only text review can use a source-backed result before that full viewer exists; it is not billed as the finished visual episode.

## 5. Change and preserve contract

A review request binds candidate ID/hash, source base, criteria revision, target components/files, change instructions and explicit preservation assertions. Use actual registered targets; an ambiguous spatial reference is clarified or highlighted against the known candidate. Do not claim a pixel observation grants authorization or proves exact text.

For component-scoped transformations, stage only the allowed writable unit and recompose from retained versions. For ordinary repository coding with a broader working tree, a prompt cannot guarantee untouched siblings: use diff/scope checks and relevant rendered/behavioral tests before candidate promotion. Report which guarantee actually applies. Shared CSS or APIs can affect other components even when their source files are unchanged.

Keep the previous useful preview while a new candidate is checked. Publish atomically after required checks, then offer review. Independent review, human acceptance, code merge and deployment remain separate. A failed candidate never replaces the accepted version merely because a native worker emitted “done.”

## 6. UI proof

Use synthetic fixtures early, then real source-linked scenarios. Test laptop and narrow mobile layouts, keyboard operation, zoom/reduced motion, simultaneous conversation/brief, two users, lost network, stale events and a typed-tool continuation during active voice. Include English, Italian and Spanish input examples without assuming one classifier language benchmark establishes runtime quality.

No new pixel design is included in this pack. Luis owns the visual integration; the acceptance criteria bind behavior and truthful states, not a speculative screenshot.
