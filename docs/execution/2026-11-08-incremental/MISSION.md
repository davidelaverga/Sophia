# Mission — useful connected resources and continuous work

**Mission ID:** SOPHIA-INC-2026-11  
**Version:** Specs pack v2, 8 November 2026  
**Implementation state at issue:** not_started  
**Release audience:** Davide and Luis; not a general-availability claim

## 1. Mission goal

Davide and Luis can each connect their own Codex and Claude Code subscriptions through qualified owner-bound execution; use a permitted API resource for Explore; turn a specific project request or accepted exploration result into repository work; inspect and change resource, model, and effort choices; and follow or guide Sophia's project manager through typed and qualified voice interaction.

The programme is complete when these defined capabilities are merged into main, deployed to the intended Sophia environment, and exercised successfully in the application by the independent Codex reviewer/tester. Exact source, runtime, configuration, and release evidence must be retained.

Conversation requires no mandatory intent selector. Sophia distinguishes who can read a message, whom it addresses, what it asks, and what effect is currently authorized. A classification never grants authority by itself.

## 3. Delivery roles and independence

One Codex coordinator owns the programme's mission ledger and prompts all other threads. Claude Code workers implement code. The Claude Code designer is an implementation role with a defined UI scope.

One separate Codex thread performs both review and application testing. It may execute an authorized deployment and inspect the real result. It records a source-review episode and an application-verification episode separately. They may share the same thread identity; they must be independent of the authoring sessions and must identify the exact artifacts they assessed.

The independent thread returns findings to the coordinator; Claude Code workers fix them. If the independent thread ever authors a substantive implementation change, its own approval of that change is not independent. Return the change for independent review under an explicit reassignment; do not silently weaken the gate.

Automatic Codex review runs after every PR push, covers every introduced commit, and must cover the current final head before merge. Current repository instructions also require an independent whole-diff review before each push. These are distinct gates.

The coordinator does not merge or deploy merely because it can issue a prompt. Existing repository and environment authority still applies. Luis's current merge/integration responsibility is preserved unless an explicit owner decision changes it.

## 5. Non-negotiable behavior

1. Persist input and dispatch intent before effects; reconcile uncertain delivery instead of duplicating it.
2. Keep one active project manager and one writer for a worktree/effect. An observation is not a second scheduler.
3. Recheck current membership, source eligibility, grants, holds, and binding before each new admitted effect.
4. Keep API funds, native allowance, voice funding, and automatic GitHub-review funding distinct.
5. Do not infer available quota from plan price, transcript tokens, context fullness, or a reset timestamp.
6. Honor explicit pins and permit only visible fallbacks within an existing allowance.
7. Preserve cumulative allowance and unsettled effects through retries, steering, repairs, restarts, and later transfers.
8. Do not expose unrelated native histories, copied consumer login tokens, private titles, or private derived summaries to another member.
9. Ordinary follow-ups queue to the project manager. Hold/Stop allows authorized reads of retained evidence, not an implicit new native inquiry turn.
10. Native acknowledgement, task completion, candidate acceptance, merge, deploy, and product verification are distinct observations.
11. Significant UI changes cannot advance through the design gate without Davide's explicit approval.
12. Recovery and rollout controls preserve existing work and records; disabling admissions does not erase or falsely settle active work.

## 6. Execution order

Start INC-00 and the first INC-01 owner/provider slice. Once one owner's Codex and Claude Code routes and session/control boundaries qualify, INC-02 may begin without waiting for the other owner or API-sharing rollout.

INC-03 contracts and routing observation can proceed in parallel with connection work. Live dispatch waits for its particular qualified action path. INC-04 automates new assignments after explicit execution works. INC-05 integrates voice and closes the two-founder journey.

Work can be parallel where writable scopes and effects are disjoint. Contract changes, authority changes, approvals, and dependent mutations remain ordered. Avoid a large branch carrying all six missions.

## 7. Programme state and completion

Track delivery phase and blockers separately. Suggested phase vocabulary is planning, implementing, reviewing, merged, deploying, verifying, and complete. Holds include awaiting_design_approval, owner_action_required, resource_wait, technical_blocker, and outcome_unknown. A hold does not erase completed evidence or create a new mission.

Programme completion requires:

- Every required acceptance case for O1–O7 passed with current evidence.
- Exact merged source and current relevant dependency/runtime identities.
- Independent source approval, current-head automatic review coverage, and required CI.
- Davide approvals for each significant delivered UI scope, with a final material-delta check.
- Verified deployment and actual in-app user journeys on the intended environment.
- Four qualified native connections, real native repository work for both founders, and real cross-member API use.
- Required typed/voice, denial, reconnect, privacy, pin, and control cases.
- No unresolved blocking finding or unknown external effect affecting the delivered outcome.
- Clear user-facing completion report, retained evidence, rollback/continuation record, and explicit deferred backlog.

A failed deployment, unavailable owner sign-in, failed UI approval, or failed app test leaves the relevant outcome open. Record the smallest next action; continue independent work.
